Introduction

Why environment setup is part of machine-learning engineering rather than administrative busywork.

─────

The course can be followed in a hosted notebook such as Google Colab or in a local virtual environment. Colab removes most machine-specific setup problems and is convenient when you need a GPU temporarily. A local environment gives you more control and is usually better once you begin building projects rather than isolated exercises.

The important idea is isolation. A Transformer project depends on several packages that evolve at different speeds. If those packages are installed globally, one experiment can silently break another. A virtual environment gives the project its own dependency set. Record versions when an experiment matters so that the same model and preprocessing path can be reproduced later.

A Hugging Face account becomes relevant when you download gated resources, authenticate from notebooks, push models or datasets, and publish demos. Authentication is a permission layer; it is not part of the Transformer model itself. Keep access tokens out of source code and public notebooks.

Choose where the course will run

The course supports two practical environments: a hosted notebook such as Google Colab, or a local Python environment. Colab is useful when you want to begin immediately or need temporary access to an accelerator without configuring drivers. A local setup is better when the course becomes a real project: you control Python versions, package versions, model caches, editor tooling, and persistent files.

Whichever route you choose, the important engineering principle is isolation. Hugging Face libraries evolve quickly and depend on PyTorch, tokenizers, numerical libraries, and optional accelerator packages. Installing everything into a system Python can make one experiment break another. A project-specific virtual environment gives the course a reproducible dependency boundary.

Install only the stack you need

The early chapters rely mainly on transformers, then later add datasets, tokenizers, evaluate, and accelerate. The demo chapter uses Gradio, the curation chapter uses Argilla, and modern LLM fine-tuning introduces TRL and PEFT. Installing the entire ecosystem on day one is convenient but can make dependency problems harder to diagnose. A cleaner habit is to add a library when the chapter first needs it and record the version.

The model weights themselves are not installed as Python packages. from_pretrained() downloads checkpoints and configuration into a cache. That distinction matters when debugging disk usage: your virtual environment contains code; the Hugging Face cache contains model and dataset artifacts.

Authentication and the Hub

A Hugging Face account is not required for every public read operation, but it becomes important when you use gated models, create repositories, push checkpoints or datasets, or deploy Spaces. Authentication is therefore a repository permission concern, not part of the model computation.

Use an access token through the supported login flow or environment/secret storage. Do not paste a write-capable token into notebooks that may be committed or shared. Later chapters treat the Hub as a versioned artifact registry, so getting the authentication boundary right at the beginning prevents a surprisingly large class of avoidable problems.

Introduction

How the course is organized and why it starts from concepts before API mechanics.

─────

This chapter deliberately begins above the code level. Before learning AutoModel, Trainer, or tokenizers, you need a vocabulary for the problem: What task are we solving? What family of model is appropriate? What was the model trained to predict? Those questions determine which API object later makes sense.

The course then moves from high-level Transformer capabilities into the mechanism that supports them. That progression matters. A pipeline call can make sentiment analysis look like a single operation, but underneath it are tokenization, numerical tensors, a pretrained Transformer, a task head, logits, and post-processing. Chapter 1 gives names to those layers so later abstractions do not feel magical.

A useful study rule is to separate three nouns: an architecture is the computational design, a checkpoint is a set of learned parameters for that design, and a task is the problem you want solved. BERT is an architecture family; a particular bert-base-* repository is a checkpoint; sentiment classification is a task.

What this chapter is really teaching

The first chapter establishes the vocabulary used throughout the course. It separates a task, an architecture, and a checkpoint. A task is the problem—classification, generation, translation, question answering. An architecture is the network design—encoder, decoder, encoder–decoder and their concrete families. A checkpoint is one trained set of weights for an architecture.

Keeping these concepts separate prevents a common beginner error: treating model names as tasks. BERT is not “sentiment analysis”; it is an encoder architecture family that can be adapted for sentiment analysis by attaching and training a suitable head. GPT-style models are not “chat”; they are causal language models that can later be instruction-tuned into chat systems.

The progression of the course

The course intentionally begins with high-level inference before exposing implementation details. You first see what pretrained models can do through pipeline(). Then the abstraction is opened: tokenizers, tensors, models and logits. Only after that does the course introduce datasets, optimization loops, tokenizer training, task-specific preprocessing, sharing, demos, human annotation, supervised LLM fine-tuning and reinforcement-learning-style post-training.

That progression is useful to keep in mind while reading. When a later chapter introduces a new API, connect it back to the same basic path: data is represented numerically, a model computes hidden states or logits, an objective or decoding procedure turns those values into behavior, and evaluation determines whether the behavior is useful.

Natural Language Processing and Large Language Models

What NLP covers, what changed with large language models, and what scale does—and does not—give us.

─────

Natural Language Processing is the broader field concerned with computational processing of human language. Classical NLP systems are often built for a particular task: text classification, named-entity recognition, question answering, translation, summarization, or generation. The input and output shapes differ, but they all require converting language into a representation a model can process.

Large language models are usually trained first on a broad language-modeling objective over very large corpora. The result is not a model that contains a neat database of facts; it is a parameterized probability model that has learned statistical structure in language. Scale can produce broad capabilities, in-context learning, and useful transfer to tasks that were not represented as explicit labeled datasets during pretraining.

The capability jump should not be confused with reliability. LLMs can generate fluent falsehoods, inherit stereotypes from training data, fail outside their context window, and be sensitive to prompt wording. Their output is produced from learned conditional probabilities. Fluency is therefore evidence of good language modeling, not proof that the generated statement is factual.

What NLP includes

Natural Language Processing is the broader discipline of getting computers to work with human language. The course uses tasks such as text classification, token classification, question answering, summarization, translation and generation because each one exposes a different output structure. A classifier predicts a small set of labels. NER predicts labels aligned with words or tokens. Extractive QA predicts a span. Translation and summarization generate new sequences.

Modern systems often solve several of these tasks with the same pretrained Transformer backbone. This reuse is one reason Transformers displaced many task-specific architectures: instead of designing a separate feature pipeline for every NLP problem, a general pretrained representation can be adapted to many outputs.

What makes an LLM different

A language model learns a probability distribution over token sequences. At large scale, next-token or masked-token objectives force a model to capture syntax, semantics, factual associations, style and many forms of statistical regularity because those patterns help predict missing or future text. A large language model is therefore not a conventional database and does not retrieve one exact stored sentence each time. It computes probabilities from learned parameters.

Scale brings broad transfer. A sufficiently capable model can often perform a new task from instructions and examples placed in the prompt. This is called in-context learning and is different from fine-tuning: the weights are unchanged; the prompt changes the conditioning context.

Capabilities do not remove limitations

Fluent output can look more certain than the underlying model warrants. LLMs may generate unsupported facts, reproduce biases in their data, fail on long contexts, or be sensitive to small prompt changes. Their training objective rewards predicting plausible continuations, not verifying every claim against an external source.

This distinction becomes central later in the course. Retrieval, domain adaptation, SFT and RL-style post-training can modify behavior, but none changes the basic requirement to evaluate models on the population, domain and failure modes of the intended application.

Transformers, what can they do?

Use `pipeline()` to learn the task landscape without yet managing tokenization and model classes manually.

─────

The pipeline() API is the course's first practical window into pretrained Transformers. It bundles preprocessing, model execution, and output post-processing behind a task-oriented interface. That makes it useful for exploration: you can compare text classification, zero-shot classification, fill-mask, named-entity recognition, question answering, summarization, translation, and text generation with very little code.

The important lesson is not the one-line syntax. It is that different tasks require different output semantics. A classifier returns scores over labels; a fill-mask model scores vocabulary candidates at a missing position; extractive QA predicts a span inside a context; a causal language model repeatedly predicts the next token. The wrapper may look uniform while the model heads and decoding logic underneath are not.

Zero-shot classification is especially useful for understanding the distinction between fixed task labels and prompt-conditioned labels. Instead of training a new classifier head for every label set, an appropriate model can score candidate labels expressed as natural language. This flexibility comes from transfer, not from the pipeline function itself.

Why `pipeline()` comes first

The pipeline() abstraction deliberately hides tokenization, model loading and post-processing. That is useful in the first chapter because it lets you compare tasks before learning the mechanics. A typical call chooses a task identifier, optionally a checkpoint, and then accepts Python-friendly inputs such as strings.

Underneath, however, the wrapper still has to choose a tokenizer or processor, convert input to tensors, execute a model with the correct task head, and transform logits or generated token IDs into human-readable output. Chapter 2 reconstructs those hidden steps manually.

Text generation

A text-generation pipeline loads a causal language model. Given a prompt, the model predicts a distribution over the vocabulary for the next token. A decoding strategy chooses one token, appends it to the context, and repeats. The returned paragraph is therefore the result of many sequential forward steps rather than one classification pass.

Generation parameters matter. The maximum number of new tokens determines when decoding stops by length; sampling controls diversity; temperature reshapes the probability distribution; top-k and top-p restrict which candidate tokens are considered. These settings alter output without changing model weights.

Classification and zero-shot classification

Ordinary text classification assumes a fixed label set learned during training. The task head produces one score for each class. Post-processing usually applies softmax for mutually exclusive labels or sigmoid for independent labels.

Zero-shot classification is different. A natural-language-inference-style model can compare the input text with candidate label descriptions formulated as hypotheses. Because the labels are supplied at inference time, the same checkpoint can rank labels it was not specifically trained to expose as a fixed classifier head. This flexibility is transfer learning in action, not magic inside the pipeline() function.

Fill-mask, NER and question answering

A fill-mask pipeline uses a masked language model and asks which vocabulary tokens are plausible at the masked position. Token classification, including named-entity recognition, returns a prediction for each relevant token and then aggregates subword pieces into user-visible spans. Extractive QA accepts a question and context and predicts start/end positions for an answer span inside the context.

These tasks look very different in a demo, but they share the same architectural pattern: preprocessing determines the tensor layout, the Transformer builds contextual hidden states, and a small task-specific output layer maps those representations to a task-shaped prediction space.

Summarization and translation

Summarization and translation are sequence-to-sequence tasks. An encoder–decoder model reads a source sequence with its encoder and generates a target sequence autoregressively with its decoder. The target language differs for translation; the target is a compressed representation for summarization.

The high-level pipeline hides generation details, but the core is the same decoder loop used elsewhere: produce vocabulary logits, choose the next token, append it, and continue until an end condition. The encoder output is available to the decoder through cross-attention during every target-generation step.

How do Transformers work?

Understand pretraining, transfer learning, attention, and the encoder/decoder building blocks.

─────

Transformer models are commonly pretrained with self-supervised objectives. The training signal is created from the text itself instead of requiring a person to label every example. A masked language model hides some tokens and learns to reconstruct them; a causal language model learns to predict future or next tokens. This turns enormous collections of raw text into training examples.

Pretraining learns general language representations, but a downstream application may need different behavior. Transfer learning reuses the pretrained parameters and adapts them with task or domain data. This is why fine-tuning a pretrained model usually needs far less labeled data and compute than training the same architecture from random weights.

The key Transformer mechanism is attention. Each token is converted into representations that generate query, key, and value vectors. Similarity between a query and keys determines how strongly information from the corresponding values contributes to the token's next representation. Multi-head attention repeats this in parallel subspaces so different relationships can be modeled simultaneously.

An encoder normally allows a token to attend to tokens on both sides, producing contextual representations of the full input. A decoder used for causal generation masks future positions: token *t* may use earlier tokens but must not see token *t+1* while predicting it. Encoder–decoder models combine a source-reading encoder with a target-generating decoder.

Pretraining and self-supervision

Transformers are usually pretrained before they are adapted to a downstream task. The critical idea is self-supervision: the training signal is created from the data itself. A causal language model predicts later tokens from earlier tokens. A masked language model hides selected tokens and learns to reconstruct them. Because raw text supplies both input and target structure, enormous corpora can be used without hand-labeling every sentence.

Pretraining is expensive but reusable. The resulting parameters encode general statistical structure of language. Fine-tuning begins from those parameters and needs much less labeled task data than a model initialized randomly.

Transfer learning

Transfer learning separates broad representation learning from task specialization. In the common workflow, a model is pretrained on a general corpus, optionally adapted further on domain text, and then fine-tuned on a narrower labeled objective. Modern instruction-tuned LLMs add one or more post-training stages after base language-model pretraining.

The same principle explains why a public checkpoint can be valuable even when its original training task differs from yours: the backbone has already learned useful representations and attention patterns. Your training stage can focus on the smaller difference between the pretrained behavior and the desired behavior.

Attention as contextual information routing

Attention lets each token compute a weighted combination of information from other tokens. Each hidden representation is projected into query, key and value vectors. The query from one position is compared with keys from visible positions. The similarity scores are normalized and used to combine the corresponding values.

This means a token representation is not fixed independently of its sentence. The representation for “bank” can draw strongly from “river” in one context and “loan” in another. Multi-head attention repeats this mechanism in several learned subspaces, allowing the layer to model different relationships in parallel.

Causal masking versus bidirectional attention

Attention is controlled by a mask. Encoder models generally allow every non-padding token to attend to the complete input, so representations can use both left and right context. A causal decoder blocks attention to future target positions. When predicting token t+1, it may use the prompt and tokens through t, but not the answer token it is supposed to predict.

Causal masking is what makes next-token training valid. Without it, a decoder could directly inspect future tokens and the learning objective would collapse into a trivial copying problem.

Encoder blocks

An encoder block combines self-attention with feed-forward transformations, residual connections and normalization. After several blocks, each position contains a context-aware representation of the complete visible input. Encoder-only checkpoints therefore work naturally for classification, token labeling and span extraction, where the input is already available in full.

Decoder blocks

A decoder block uses masked self-attention so target generation remains causal. In a decoder-only model, this is the main sequence-processing mechanism. In an encoder–decoder model, the decoder also contains cross-attention that reads encoder representations. This gives it two information sources: the target prefix generated so far and the encoded source sequence.

Autoregressive generation repeatedly reuses these decoder layers. That repeated computation is why generation latency behaves differently from classification latency and why KV caching is important in deployment.

How 🤗 Transformers solve tasks

Trace the reusable input → backbone → task head pattern behind many Transformer applications.

─────

Most task-specific Transformer models can be understood as a shared backbone plus a small output mechanism. The tokenizer first converts text into token IDs and masks. The Transformer converts those IDs into contextual hidden states. A task head then maps the hidden representation to whatever the task needs: class logits, one label per token, start/end span scores, or vocabulary logits.

This explains the difference between AutoModel and task-specific classes such as AutoModelForSequenceClassification. The base model exposes hidden representations. The task class adds the appropriate head and often computes a suitable loss when labels are supplied. The pretrained backbone supplies linguistic knowledge; the head defines the prediction geometry.

Generative language models use a language-model head that produces one score for every vocabulary token at each relevant position. Those scores become probabilities after normalization, and a decoding strategy chooses the next token. Classification instead collapses or selects a representation and projects it into a much smaller label space.

The common task pattern

The Hugging Face lesson makes a broader point than “add a head to BERT.” Across text, audio and vision, the recurring pattern is to transform raw input into a sequence of model-compatible representations, pass them through a backbone, then interpret the final hidden states with a task-specific objective or output layer.

What changes across modalities is the input representation. Text becomes token embeddings. Audio may become learned features or spectrogram representations. Images may become patch embeddings. Once those inputs are represented as sequences or grids of vectors, Transformer-style attention can operate on them.

Masked and causal language modeling

For language, the lesson distinguishes two foundational pretraining objectives. Masked language modeling lets an encoder see context on both sides of a deliberately hidden token and predict that token. Causal language modeling masks future positions and trains a decoder to predict the next token from the visible prefix.

These objectives line up with architecture. Bidirectional encoders are well suited to understanding a completed input. Causal decoders are naturally suited to generation because training and inference obey the same left-to-right information restriction.

GPT-style text generation

A GPT-style checkpoint tokenizes input, combines token and position information, and processes the sequence through causal decoder blocks. The final hidden state at each position is projected through a language-model head into one logit for every vocabulary token. During training, targets are the same token sequence shifted so that each position learns to predict what comes next.

At inference, the final position's logits are converted into a token choice, the selected token is appended, and the model runs again. This simple objective scales into chat and code generation after appropriate post-training.

BERT text classification

BERT uses a bidirectional encoder. The input convention includes special tokens such as [CLS] at the beginning and [SEP] between sequences. The final representation associated with a pooled or special position can be fed to a classification head that returns logits over task labels.

Pretraining and downstream classification are separate stages. BERT's original pretraining uses masked-language modeling and, in the original formulation, next-sentence prediction. A downstream classifier then updates the pretrained network and newly initialized task head using labeled examples.

Token classification and named entities

For token classification, the backbone still produces one contextual hidden vector per input token, but the head projects every token vector into label logits. Named-entity recognition can therefore label a span as person, organization, location and so on.

Subword tokenization complicates the label mapping because one original word may correspond to several model tokens. Chapter 7 returns to that problem and uses fast-tokenizer alignment metadata to construct valid labels.

Extractive question answering

BERT-style extractive QA uses the complete question and context as input. A span head produces a start score and an end score for each token position. The system selects a plausible pair of positions and maps that token span back to the original context text.

This is different from generative QA. The extractive model is not free to invent arbitrary answer text; the answer is constrained to a span already present in the context.

BART-style summarization

Encoder–decoder models such as BART are designed for sequence transformation. BART is pretrained as a denoising autoencoder: input text is corrupted, the encoder represents the corrupted sequence, and the decoder reconstructs the original. This teaches the model to generate coherent text conditioned on an encoded source.

For summarization, the same architecture is fine-tuned so the target sequence is a shorter summary rather than a reconstruction. Cross-attention gives the decoder access to source information while it generates the target token by token.

Translation

Translation has the same source-to-target structure as summarization. An encoder represents text in the source language and a decoder generates target-language tokens. Multilingual models extend this with training across many languages and may use language identifiers or task prefixes to tell the model which translation direction is required.

Speech and audio

Transformers also operate beyond text. Whisper, for example, converts audio into a log-Mel spectrogram, encodes that representation and then uses a text decoder to generate transcripts or translations. Special decoder tokens can steer language identification, transcription or translation behavior.

The important abstraction is that the encoder does not care that the original source was text or audio once it has been converted into the model's expected vector sequence. Modality-specific preprocessing happens before the Transformer backbone.

Computer vision

Vision Transformer (ViT) treats an image as a sequence of patches. Each image patch is projected into a vector, positional information is added, and a learnable classification token is processed together with the patch sequence by Transformer encoder layers. The final classification representation feeds an image-classification head.

The lesson also contrasts attention-based vision models with modern convolutional models such as ConvNeXT and introduces task-specialized architectures for object detection, segmentation and depth estimation. The general message is that Transformer ideas are reusable, but input representation and output head still have to match the task.

Transformer Architectures

Choose an architecture by asking what information each prediction is allowed to use.

─────

Encoder-only models such as BERT are naturally suited to understanding tasks. Because their self-attention is usually bidirectional, each token representation can incorporate both left and right context. That is valuable for sentence classification, token classification, semantic representations, and extractive question answering.

Decoder-only models such as GPT-style models use causal self-attention. During training and generation, a position cannot use future target tokens. This matches autoregressive generation: estimate the distribution of the next token given everything generated so far, select a token, append it, and repeat. Modern chat LLMs are predominantly decoder-only.

Encoder–decoder models such as T5 and BART separate reading from generation. The encoder builds representations of the source sequence; the decoder attends both to earlier target tokens and to encoder outputs. This makes the architecture intuitive for sequence-to-sequence tasks such as translation and summarization.

The architecture is therefore an information-flow decision rather than a popularity contest. If the task needs a representation of an already-complete input, an encoder is efficient. If the task must freely continue text, use a decoder. If the output is a transformed sequence conditioned on a source sequence, encoder–decoder is often a strong fit.

Encoder-only models

Encoder-only Transformers read an input bidirectionally. Self-attention at a token can use information from both earlier and later visible tokens, producing rich contextual representations. BERT and related models are therefore natural for understanding-oriented tasks where the whole input is known before prediction.

Typical uses include sentence classification, semantic similarity, named-entity recognition and extractive question answering. The downstream head changes, but the encoder's job remains to represent the completed input.

Decoder-only models

Decoder-only models use causal attention. Each target position can attend only to the prompt and earlier generated tokens. That information-flow rule matches next-token language modeling exactly and is why decoder-only architectures dominate modern open-ended generation.

GPT, Llama, Gemma and many contemporary chat models belong to this broad family. Chat behavior comes from post-training and formatting conventions layered on top of the base causal architecture.

Encoder–decoder models

An encoder–decoder model splits source understanding from target generation. The encoder can read a source bidirectionally. The decoder uses causal self-attention over the target prefix plus cross-attention to encoder states. Translation, summarization and many structured sequence-to-sequence tasks fit this pattern naturally.

T5 reframes many tasks as text-to-text transformations, while BART is pretrained as a denoising sequence autoencoder. Their differences matter, but both share the same two-part information flow.

Choose by information flow, not popularity

Architecture choice is easiest when expressed as a question: what information is each prediction allowed to use? If the model is labeling an already-complete sentence, bidirectional context is useful. If it is generating the future of a sequence, future target tokens must be hidden. If it must transform one complete sequence into another sequence, separate encoder and decoder roles are often helpful.

This mental model remains useful even when a modern decoder LLM can technically perform many tasks through prompting. A smaller encoder can still be the better engineering choice for a fixed classifier because it may be cheaper, faster and easier to validate.

Inference with LLMs

What actually happens after you submit a prompt to a decoder language model.

─────

LLM inference is an iterative probability calculation. The prompt is tokenized, the model computes logits for the next position, a decoding rule selects a token, and that token is appended to the sequence. The model then repeats the process until it reaches a stopping criterion such as an end token or a maximum number of generated tokens.

Generation speed therefore differs from a one-shot classifier. A classifier can usually produce its output from one forward computation over the input. Autoregressive generation needs repeated steps. Implementations cache attention keys and values from earlier tokens so they do not recompute the entire history every step; this KV cache improves speed but consumes memory that grows with context and batch size.

The context window is the maximum token span the model can process for a request. Prompt tokens, retrieved text, chat history, and generated tokens all compete for this budget. Context is not long-term memory. If relevant information falls outside the visible window or is never supplied, the model cannot directly attend to it.

Finally, the model produces a distribution, not the final wording itself. Greedy decoding, temperature-controlled sampling, top-k/top-p sampling, beam-like strategies, and stop conditions change which trajectory is selected from the same underlying probabilities.

Inference is sequential generation

During LLM inference, a trained causal model is repeatedly asked the same question in slightly different contexts: given all tokens so far, what should the next-token distribution be? The first forward pass processes the prompt. A decoding policy chooses a token. That token becomes part of the context and another step computes the next distribution.

The apparent single response in a chat UI can therefore represent hundreds of model steps. This is one reason generation has different latency and throughput characteristics from one-pass classification.

Attention during generation

Attention lets the next position retrieve information from relevant earlier tokens. In a prompt about the capital of France, representations associated with “capital” and “France” can contribute strongly to the hidden state used to predict “Paris.” Attention is learned and context-dependent; the model is not following a hand-written lookup rule.

As context grows, each new token potentially needs information from a larger prefix. Efficient inference implementations cache previously computed key and value tensors so earlier positions do not need to be recomputed from scratch for every next token.

Context length

The context window is a maximum token budget for a request. System instructions, conversation history, user input, retrieved documents and generated output all consume this budget. If the prompt plus requested generation exceeds what the architecture or serving configuration supports, input must be truncated, compressed, chunked or otherwise managed.

Context is working memory, not persistent model memory. Text that is outside the window cannot be directly attended to during that request. This is why retrieval systems and conversation-memory systems have to decide what information to place back into the current context.

Prompting

A prompt is the conditioning sequence supplied before generation. Instruction wording, examples, separators, role markers and ordering all change the model's visible context and therefore the next-token distribution. Prompt engineering is fundamentally input design.

For instruct models, raw user text is usually serialized through a chat template before tokenization. Chapter 11 explains why using the checkpoint's expected role/special-token format matters.

Decoding controls

Model logits specify relative preference over vocabulary tokens, but a separate decoding algorithm chooses which token is emitted. Greedy decoding chooses the highest-probability token. Sampling draws from a distribution. Temperature can sharpen or flatten that distribution, while top-k and top-p restrict the candidate set.

These controls affect creativity, determinism and error patterns without retraining the model. They should be evaluated as part of the serving configuration rather than treated as decorative UI sliders.

Inference cost and serving

Autoregressive generation cost grows with prompt length, output length and batch/concurrency. The KV cache accelerates decoding but consumes memory proportional to the stored context and number of active sequences. This creates practical trade-offs between long contexts, large batches and throughput.

Later deployment material builds on this idea: model quantization reduces weight memory, specialized runtimes improve kernel efficiency, and request schedulers batch token-generation work across users.

Bias and limitations

Treat model behavior as learned statistical behavior that must be evaluated, not trusted by default.

─────

Pretrained models inherit patterns from the corpora used to train them. If occupational descriptions, demographic associations, dialects, languages, or viewpoints are unevenly represented, the model can reproduce those imbalances. The course demonstrates this idea with masked-language-model predictions: apparently neutral prompts can expose learned social associations.

Fine-tuning does not automatically remove those patterns. A downstream dataset may reduce, preserve, or even amplify them. Evaluation therefore has to match the population and failure costs of the real application. A model that looks strong on an aggregate benchmark can still fail systematically for a subgroup or uncommon language variety.

Generative models add another limitation: they can produce plausible text unsupported by evidence. Hallucination is a consequence of optimizing language-model objectives, not a rare parser bug. Grounding, retrieval, constrained outputs, verification, and human review can reduce risk, but none turns probabilistic generation into guaranteed truth.

Where bias comes from

A model learns statistical associations from its training corpus. If particular demographic groups, occupations, dialects or viewpoints are represented unevenly, those patterns can appear in predictions and generations. A masked-language-model probe can reveal associations by observing which tokens the model considers likely in otherwise similar contexts.

Bias is not restricted to obviously offensive outputs. It can appear as systematically different confidence, representation quality or error rates for subgroups and languages.

Why fine-tuning is not a reset button

Fine-tuning begins from pretrained parameters, so the starting representation already contains learned associations. A small downstream dataset may not contain enough counter-evidence to remove them; in some cases it can introduce new imbalance. Evaluation should therefore include subgroup and domain analysis rather than assuming that a high average metric proves fair behavior.

Generative models optimize token prediction, not truth verification. They can produce text that is locally coherent and stylistically confident while unsupported by evidence. Retrieval and tool use can ground responses in external sources, but the application still needs verification logic when mistakes carry cost.

Context and distribution limits

Performance is strongest near distributions represented in training and evaluation. Rare languages, unusual formats, adversarial prompts and long-context reasoning can expose weaknesses that are invisible in headline benchmarks. The correct response is measurement: test on representative data and record where the model should not be trusted.

Behind the pipeline

Decompose a classification pipeline into preprocessing, model execution, and post-processing.

─────

A typical text-classification pipeline first loads the tokenizer associated with the checkpoint. The tokenizer turns one or more strings into model inputs such as input_ids and attention_mask, often returned as framework tensors. The IDs are vocabulary indices; the mask tells the model which positions are real input rather than padding.

The base Transformer produces hidden states with a shape conceptually like [batch_size, sequence_length, hidden_size]. A sequence-classification class adds a head that maps a suitable representation to logits with shape [batch_size, number_of_labels]. Logits are raw scores; they are not probabilities.

Post-processing applies a normalization such as softmax for mutually exclusive classes and uses the model configuration's label mapping to turn numeric class IDs into names. Understanding this chain is useful because every bug can now be localized: bad text preparation, bad tensor shape, wrong model/head, or wrong interpretation of logits.

Step 1: preprocessing

The tokenizer converts text into integer token IDs. It may also add special tokens and return an attention_mask. For a batch, the output is a dictionary of tensors whose first dimension is the number of examples and whose second dimension is the padded sequence length.

The IDs are not meaningful by themselves. ID 101 means whatever token occupies index 101 in that tokenizer's vocabulary. This is why the tokenizer must match the checkpoint.

Step 2: model execution

Passing the tokenizer dictionary with model(**inputs) feeds the expected tensors into the network. A base Transformer produces hidden representations. A task-specific class adds an output head and returns logits shaped for the task.

For sequence classification, logits usually have shape [batch, num_labels]. They are raw, unnormalized scores. Applying softmax produces a probability distribution when the classes are mutually exclusive.

Step 3: post-processing

The model configuration contains mappings between numeric class indices and human-readable labels. Post-processing pairs the normalized scores with those labels, which is what pipeline() returned in Chapter 1.

This decomposition gives you three independent debugging boundaries: verify tokenization, verify tensor/model output, then verify score interpretation. It is much easier to diagnose a strange result when you know which boundary is wrong.

Hidden-state shape

A Transformer backbone commonly produces hidden states shaped [batch_size, sequence_length, hidden_size]. The hidden size is an architectural dimension; every token position receives one contextual vector. Different task heads reduce or project those token vectors differently.

Sequence classification may use a pooled/special representation. Token classification projects each token. QA produces start/end scores per token. A causal LM projects token states into vocabulary logits.

Why logits are not probabilities

A logit can be any real number. Softmax converts a vector of logits into non-negative values that sum to one. Because softmax is monotonic with respect to relative logit size, argmax gives the same winning class before and after softmax, but the normalized scores are easier to interpret.

Do not blindly apply softmax to every model output. Multi-label classification commonly uses independent sigmoid probabilities, and regression heads may output direct scalar values.

Tokenizers

Why tokenization is a design trade-off between vocabulary size, unknown tokens, sequence length, and linguistic reuse.

─────

A word-level tokenizer is easy to understand: split text into words and assign each word an integer. Its problem is vocabulary explosion. Morphological variants such as run, runs, and running occupy separate entries, rare words become unknown tokens, and truly broad language coverage becomes impractical.

A character tokenizer solves most unknown-word problems because a small set of characters can compose many strings. The cost is sequence length. A word that was one token may become ten characters, making attention more expensive and forcing the model to reconstruct word-level structure from longer sequences.

Subword methods occupy the middle ground. Frequent words can stay intact while rare words are decomposed into reusable pieces. That gives a manageable vocabulary, low unknown-token frequency, and much shorter sequences than pure character tokenization. BPE, WordPiece, and Unigram are different algorithms for learning or selecting those pieces; Chapter 6 studies them precisely.

Encoding has two conceptual steps: tokenize the string into token pieces, then map pieces through the tokenizer vocabulary to integer IDs. Decoding reverses IDs back toward readable text. The same tokenizer used during model training must normally be used at inference because an ID only has meaning relative to that vocabulary.

Word tokenization

A word tokenizer is intuitive because tokens line up with visible words, but real language makes the vocabulary explode. Inflection, punctuation, spelling variants and named entities create huge numbers of low-frequency forms. Anything outside the fixed vocabulary needs an unknown token, which destroys lexical information.

Character tokenization

Character-level tokenization almost eliminates unknown tokens because a small alphabet can spell arbitrary words. The problem is sequence length. Words that were single tokens become many positions, making attention more expensive and forcing the model to learn word structure over much longer sequences.

Subword tokenization

Subword algorithms use frequent strings as tokens and decompose rare strings into smaller reusable pieces. Common words may remain one token; an uncommon derivative can share roots or character sequences with vocabulary pieces already learned.

This balances vocabulary size against sequence length and is why BPE, WordPiece and Unigram are widespread. Chapter 6 later derives their training algorithms rather than treating “subword” as one method.

Encoding and decoding

Tokenization produces pieces; vocabulary lookup converts those pieces to integer IDs. Decoding maps IDs back to token strings and applies model-specific reconstruction rules so spaces and continuation markers become readable text.

Decode a few model inputs whenever preprocessing matters. It is one of the fastest ways to discover that truncation removed the answer, a separator is missing or a tokenizer is not the one you expected.

Special tokens

Special tokens carry structural meaning rather than ordinary lexical content. Encoder checkpoints may use classification, separator, mask and padding tokens. Chat LLMs can use role and message-boundary tokens. The exact IDs and placement are part of the tokenizer/checkpoint contract.

Adding or changing special tokens can require resizing model embeddings and additional training. Treat vocabulary changes as model changes, not mere string formatting.

Handling multiple sequences

Make variable-length text compatible with rectangular tensor batches without letting padding corrupt attention.

─────

Neural-network frameworks batch examples into rectangular tensors. Natural-language sequences are not naturally the same length, so a batch needs a policy. Padding adds a dedicated pad token to shorter examples. Truncation removes tokens when a sequence exceeds a chosen or model-supported maximum length.

Padding only works correctly when the model is told which positions are artificial. The attention_mask normally contains 1 for real tokens and 0 for padded positions. The Transformer uses that mask so padding does not contribute as if it were language. This is why manually padding IDs but forgetting the mask can change predictions.

Padding to a fixed global maximum is simple but often wasteful. Padding dynamically to the longest example in a batch usually reduces unnecessary attention computation. Truncation is more dangerous: it destroys information. For sentence pairs or long documents you must decide which sequence to truncate and whether sliding windows or chunking are needed instead.

Different architectures may expect left padding or right padding during generation, and not all models use token_type_ids. Let the checkpoint's tokenizer encode these conventions whenever possible instead of manually constructing special-token layouts.

Why batches need padding

Deep-learning frameworks represent a batch as a rectangular tensor. Natural-language examples have different lengths, so shorter sequences must be extended to the same batch length. Padding inserts a dedicated pad token until the shapes match.

Padding is computational scaffolding, not meaningful language. The model must know which positions are artificial.

Attention masks

The attention_mask usually contains 1 for real input positions and 0 for padding. Attention uses this mask so padded values do not influence hidden representations. If you manually pad IDs but forget the mask, the model can treat pad embeddings as genuine context and produce different results.

Dynamic versus fixed padding

Padding every example to the model's global maximum length wastes computation when most inputs are short. Dynamic padding waits until batch construction and pads only to the longest example in that batch. The course uses this pattern heavily during fine-tuning through data collators.

Fixed padding can still be useful for hardware/compiler constraints or highly regular serving workloads, but it should be a deliberate performance choice.

Truncation

Truncation discards tokens beyond a selected limit. Unlike padding, it destroys information. For paired inputs you can choose which side is allowed to truncate. For long documents, simple truncation may be unacceptable; chunking and overlapping windows preserve coverage at the cost of more examples.

Always distinguish a model error from an input-loss error. If the answer was truncated before inference, no amount of fine-tuning can recover it from that request.

Batching several sequences

The tokenizer accepts lists of strings and can pad/truncate the whole batch consistently. The first tensor dimension becomes batch size. Batching improves hardware utilization because matrix operations process several examples together, though it increases memory use.

Generation serving adds another complication because sequences finish at different times. Specialized inference runtimes use dynamic or continuous batching to keep accelerators busy as requests enter and leave.

Optimized Inference Deployment

Think about serving as a different workload from training.

─────

A model that trains correctly is not automatically efficient to serve. Training optimizes repeated forward and backward passes over known batches; serving must handle request latency, concurrency, memory limits, variable sequence lengths, and often autoregressive generation. Deployment therefore introduces another layer of engineering choices.

Lower numerical precision and quantization can shrink weights and reduce memory bandwidth. Efficient batching raises throughput by processing compatible requests together, although waiting to form a batch can increase latency. Decoder models additionally maintain a KV cache during generation, so memory use depends not only on parameter count but also on batch size and context/generation length.

Specialized inference runtimes can fuse operations, optimize kernels, compile graphs, or schedule continuous batches more effectively than a general training loop. The correct target metric depends on the product: interactive chat cares strongly about time-to-first-token and token latency, while offline processing may prioritize total throughput.

Optimization must be measured end-to-end. A smaller precision format can improve speed on supported hardware but hurt on unsupported hardware; larger batches can improve device utilization while violating latency requirements. Benchmark with realistic prompt lengths, output lengths, and concurrency.

Training and serving are different workloads

Training processes known batches and performs both forward and backward passes. Serving handles variable request arrival, prompt lengths, output lengths, concurrency and latency expectations. A checkpoint that trains correctly may be wasteful or unusable as a production inference service without additional optimization.

Latency versus throughput

Latency measures how long an individual request waits. Throughput measures how much total work the system completes per unit time—requests per second or generated tokens per second. Larger batches often improve throughput by increasing accelerator utilization, but waiting to form those batches can increase latency.

Interactive chat also distinguishes time to first token from steady-state inter-token latency. A user may tolerate a long total answer if generation starts quickly, whereas an API doing offline extraction may care only about overall throughput.

Precision and quantization

Reducing numerical precision shrinks weight memory and can improve memory bandwidth and compute efficiency on hardware that supports the chosen format. Quantization represents weights, and sometimes activations/cache, with fewer bits. This can make larger models fit on one device but may introduce accuracy changes and hardware-specific trade-offs.

KV-cache memory

Decoder generation stores attention key/value tensors for the prompt and generated prefix so they do not need to be recomputed at every step. The cache makes decoding much faster, but its size grows with sequence length, layers, batch/concurrency and representation precision.

This is why long-context serving can run out of memory even when the model weights themselves fit comfortably.

Optimized runtimes

Deployment systems can fuse kernels, compile model graphs, batch token steps continuously and manage caches more efficiently than a generic training-oriented forward loop. The best runtime depends on hardware, model family and workload.

Measure with realistic prompts and generations. A benchmark with 16-token prompts tells you little about a product that regularly supplies 20,000-token contexts.

─────

Trainer packages the repetitive training machinery around a Transformers model: batching, forward passes, loss backpropagation, optimizer/scheduler integration, evaluation cadence, checkpointing, logging, and device/distributed coordination. TrainingArguments describes how that process should run.

The model still needs the correct task head. For sequence classification, AutoModelForSequenceClassification loads the pretrained backbone and a classifier head sized to num_labels. Evaluation is a separate design decision. Model output contains logits, so a metric function converts those logits into predictions and compares them with labels. Accuracy may be appropriate for one task; F1, precision/recall, BLEU, ROUGE, exact match, or domain metrics may be better elsewhere. A reproducible run records these arguments together with checkpoint revision and dataset version.

What Trainer receives

A Trainer combines the model, training/evaluation datasets, a tokenizer or processing class where needed, a data collator and a metric callback. It constructs batches, moves tensors to the appropriate device, calls the model and performs optimization.

Because Transformers task models compute loss when labels are included, Trainer often does not need a custom loss function for standard tasks.

Metrics from logits

During evaluation, the model returns logits. A metric function converts them into task predictions—commonly argmax for single-label classification—and compares those predictions with reference labels.

A full training loop

Expose every optimization step that Trainer normally performs.

─────

A manual loop starts with DataLoaders for train and evaluation splits. Each training batch is sent through the model; because labels are present, the forward pass returns a scalar loss. Calling loss.backward() computes gradients for trainable parameters. optimizer.step() applies the update, the learning-rate scheduler advances, and gradients are cleared before the next accumulation cycle.

The order is not arbitrary. Backpropagation populates gradients; the optimizer consumes them. If gradients are never cleared, they accumulate. If the scheduler is stepped at the wrong cadence, the planned learning-rate curve changes. Understanding these mechanics is what lets you implement gradient accumulation, clipping, mixed precision, or custom losses later.

Evaluation uses model.eval() and disables gradient recording. This changes behavior of layers such as dropout and avoids storing backward information. Predictions and labels are accumulated into an evaluation metric. Returning to model.train() restores training behavior.

Accelerate keeps the loop conceptually the same while handling device placement and distributed execution. Instead of rewriting code around GPUs/processes, you prepare the model, optimizer, and data loaders with Accelerator, then use its backward and gather utilities where required.

Prepare datasets for a manual DataLoader

A native PyTorch loop needs batches of tensors with the keys the model accepts. Remove unused string columns, rename the task label column to labels when appropriate, set the dataset format to return tensors and construct DataLoaders with the collator.

Inspect one batch before training. Print shapes and types. This catches most interface errors before gradients enter the picture.

Forward pass and loss

Calling model(**batch) returns task outputs. When the batch includes labels, a standard Transformers task model usually computes its own scalar loss. That loss is a differentiable function of the current parameters and batch targets.

Backward pass

loss.backward() traverses the computation graph in reverse and accumulates gradients into each trainable parameter's .grad field. Backward does not update the model. It only computes the derivatives the optimizer will use.

Gradients accumulate by default. This behavior enables gradient accumulation intentionally, but it also means you must clear them at the correct time.

Optimizer and scheduler

optimizer.step() changes parameter values using the accumulated gradients and optimizer state. A learning-rate scheduler changes the step size over training; warmup schedules are common for Transformer fine-tuning because they avoid large early updates before optimization stabilizes.

After the update, clear gradients with optimizer.zero_grad() unless you are intentionally accumulating them across several mini-batches.

Evaluation mode

Switch to model.eval() for evaluation and disable gradient recording with torch.no_grad() or inference mode. Evaluation mode changes layers such as dropout, and disabling autograd saves memory and compute.

After evaluation, return to model.train() before the next training phase.

Using Accelerate

Accelerate wraps the model, optimizer and DataLoaders so the same loop can run on available accelerators or multiple processes with minimal device-specific code. accelerator.prepare() handles placement/distribution and accelerator.backward(loss) performs an appropriate backward pass.

The conceptual order remains unchanged. Accelerate scales the loop; it does not replace the optimization mechanics.

Gradient accumulation and clipping

If one useful effective batch does not fit in memory, divide it into several mini-batches, scale/accumulate their gradients and call the optimizer only after the chosen number of accumulation steps. Gradient clipping limits exceptionally large gradient norms and can stabilize training.

These features make more sense once you understand that .backward() and .step() are separate operations.

Understanding Learning Curves

Use training and validation trends as diagnostic evidence rather than treating the final metric as the whole story.

─────

A learning curve plots an optimization or task metric against training progress. Training loss tells you how well the model is fitting examples it updates on. Validation loss or metrics estimate performance on held-out examples. The relationship between those curves is more informative than either number alone.

If training and validation performance both remain poor, the model may be underfitting: it has not learned enough from the available setup. More training, a better learning rate, better input representation, more suitable model capacity, or cleaner data may help. If training continues improving while validation degrades, the gap is evidence of overfitting: optimization is specializing to the training sample instead of improving generalization.

The lowest validation loss and the highest task metric need not occur at the same step, especially with imbalanced or structured tasks. Select checkpoints using the metric that matches your objective. Curves are also useful for detecting unstable optimization, excessive learning rates, or a run that plateaued early.

Do not infer too much from one noisy mini-batch. Use sufficiently frequent but meaningful evaluations and compare repeated runs when decisions are sensitive.

What a learning curve shows

A learning curve plots a quantity such as loss or accuracy against training progress. Training loss measures fit on examples used for updates. Validation loss measures generalization to held-out data. Looking at both trends tells you more than the final checkpoint alone.

Healthy learning

In a healthy run, training loss decreases and validation performance improves. Eventually both may plateau. Additional epochs after the plateau may waste compute unless the learning rate or data regime changes.

Underfitting

If training and validation performance are both poor, the model is not even fitting the training problem well. Possible causes include too little optimization, an unsuitable learning rate, insufficient model capacity, noisy/incorrect labels, or a preprocessing pipeline that removes necessary information.

More data does not automatically solve underfitting if the model never learns the current examples.

Overfitting

If training performance continues improving while validation performance gets worse, the model is specializing to training idiosyncrasies. Remedies can include earlier stopping, more representative data, regularization, smaller capacity or different augmentation.

The best checkpoint may therefore occur before the final epoch. Save/evaluate periodically rather than assuming “last” means “best.”

Loss versus task metric

The optimization loss and your evaluation metric measure different things. Cross-entropy can keep improving even when the discrete metric changes little, and a metric can fluctuate because a few examples cross a decision boundary. Use both.

For imbalanced tasks, class-wise metrics can reveal degradation hidden by the average.

Big data? 🤗 Datasets to the rescue!

Understand why dataset size does not have to equal Python RAM usage.

─────

Arrow-backed datasets can be memory-mapped. Instead of loading the entire dataset into Python objects, the process maps file-backed pages into its address space and the operating system loads data as needed. This allows random-access style workflows over datasets much larger than available RAM while keeping serialization overhead low.

Streaming goes further: examples are produced as an iterable without first downloading and materializing the entire corpus. This is useful for enormous or remote datasets, fast inspection, and training where sequential iteration is sufficient. The trade-off is that an iterable dataset cannot support every random-access operation with the same semantics as a materialized dataset.

Shuffle in streaming mode is approximate and buffer-based rather than a perfect permutation of all rows. Operations that require knowing or revisiting the whole dataset may also be unavailable or expensive. Choose memory mapping when you need indexed access to a materialized dataset; choose streaming when total size or download cost makes materialization undesirable.

Apache Arrow storage

Datasets uses Arrow's columnar representation so typed data can be read efficiently without reconstructing every row as a Python object. Columnar storage is particularly effective when an operation touches only a subset of fields.

Memory mapping

A materialized Dataset can be memory-mapped from disk. The process receives a virtual address mapping for the file, while the operating system loads pages as they are accessed. This means a dataset much larger than RAM can still support indexed access without a gigantic up-front Python allocation.

Memory mapping is why load_dataset() can appear to “load” a large dataset surprisingly quickly after it has been prepared in Arrow form.

Streaming

With streaming enabled, examples are produced as an iterable directly from the source instead of first downloading and materializing the complete dataset. This is valuable for huge corpora, quick inspection or training pipelines that only require sequential passes.

The return type behaves more like an IterableDataset; you cannot assume arbitrary random indexing or every operation available on a materialized Dataset.

Streaming shuffle

A true global random permutation requires access to all rows. Streaming therefore uses a shuffle buffer: maintain a window of examples, randomly emit from that window and replenish it from the stream. Larger buffers approximate a global shuffle better but use more memory.

This is an important semantic difference. shuffle() has different guarantees depending on whether the dataset is materialized or streamed.

Sharding and distributed iteration

Large streaming datasets can be split across workers or processes so each trainer consumes a different shard. Correct sharding prevents duplicate work and helps scale input throughput with distributed training.

Always reason about epoch semantics: when data is an unbounded or enormous stream, “one epoch” may not mean the same thing as one pass through a small indexed dataset.

When to choose each mode

Use ordinary/memory-mapped Datasets when you need repeatable random access, global operations and the source can be materialized. Use streaming when storage or download size is the limiting factor and your algorithm can work through sequential iteration.

Do not select streaming merely because it sounds more scalable; some preprocessing and evaluation workflows are substantially easier with a materialized artifact.

An embedding model turns token-level model outputs into one vector per passage. Pooling is the reduction step; the course demonstrates a CLS-style representation. The resulting NumPy vectors are stored in a dataset column. The same embedding function is used for the query so query and documents inhabit the same vector space.

FAISS builds an index over those embeddings. add_faiss_index() attaches the index to a Dataset column; nearest-neighbor lookup returns the candidate rows whose vectors are most similar to the query vector. This architecture—chunk/document embedding + vector index + query embedding + retrieval—is the retrieval core later used in many RAG systems.

Keyword search versus semantic search

Keyword search looks for literal lexical overlap. It is excellent when exact terms matter, but it can miss conceptual equivalence. Semantic search embeds text into a vector space so passages with similar meaning can be near one another even when they use different words.

This changes the retrieval problem from matching strings to nearest-neighbor search over vectors.

Prepare searchable passages

Retrieval quality depends heavily on what you choose to embed. The GitHub-issues example removes fields that are not useful for search, explodes comments, filters very short entries and concatenates title, issue description and comment text so each vector has enough context.

If the passage is too small, its meaning may be ambiguous. If it is too large, unrelated topics are averaged into one embedding and token limits may truncate useful details.

Choose an embedding model

An embedding checkpoint converts text into token-level hidden states. A pooling strategy reduces those states to one fixed-size vector per passage. Some sentence-transformer-style models are explicitly trained so cosine or dot-product similarity corresponds to semantic similarity; generic hidden states may be less effective.

The query must be embedded with a compatible model and preprocessing so query and documents occupy the same vector space.

Pooling

A base encoder returns one vector per token. To index one vector per passage, combine or select token representations. The course demonstrates a CLS-style representation; other embedding models use mean pooling or learned pooling.

Pooling is part of the embedding model contract. Copying a pooling function from another checkpoint can substantially change retrieval quality.

Store embeddings in the Dataset

A batched map() can run the embedding function and add an embedding column. Storing vectors alongside source text preserves the relationship between nearest-neighbor results and the original records.

For very large corpora, production systems may store vectors in a dedicated vector database or index service, but the conceptual pipeline is unchanged.

Build a FAISS index

FAISS provides efficient nearest-neighbor search over dense vectors. add_faiss_index() can attach an index to a Dataset embedding column. Internally, FAISS can use several index types with different memory, accuracy and speed trade-offs; a simple exact index is enough to learn the workflow.

Index construction is separate from embedding computation. If you change the embedding model, the old index is no longer semantically compatible and must be rebuilt.

Embed and search a query

Convert the user's query with the same embedding pipeline, then ask the FAISS index for the nearest vectors. The returned scores and indices identify Dataset rows that can be displayed or passed to a later generative system.

Always inspect retrieved text manually. A search stack can be numerically correct while semantically poor because the chunks, embedding model or corpus are wrong.

From semantic search to RAG

Retrieval-Augmented Generation adds a generative model after this retrieval stage. Retrieved passages are placed into the LLM context together with the question so generation can be grounded in external data. The retrieval system remains independently evaluable: first ask whether it finds the right evidence, then ask whether the generator uses that evidence correctly.

This separation is important when debugging RAG. If the right document never enters the prompt, blaming the LLM is useless.

Fast tokenizers' special powers

Use source-to-token alignment information that ordinary token IDs cannot provide.

─────

Fast tokenizers are backed by the Rust tokenizers implementation and are optimized for high-throughput batch processing. Their deeper advantage is alignment metadata. A BatchEncoding can retain offsets that map each generated token back to a character span in the original text and methods that connect tokens to source words.

That mapping is critical whenever prediction is made at token level but the user cares about original text. Named-entity recognition, highlighting, span extraction, and annotation tools need to know exactly which original characters correspond to a predicted token.

Subword splitting makes naïve indexing unreliable. One source word may become several tokens, while special tokens correspond to no source word. Alignment methods let you handle that explicitly rather than guessing based on token strings such as ## prefixes.

Offsets also make debugging more rigorous. You can inspect a token ID, decode its token, and point to the exact source slice that produced it.

Why fast tokenizers matter

Fast tokenizers are backed by the Rust tokenizers implementation and can process batches efficiently, but speed is only half the story. They expose alignment metadata that connects transformed model tokens back to the original text.

BatchEncoding

The tokenizer returns a BatchEncoding, a dictionary-like object containing fields such as token IDs and attention masks plus helper methods. When a fast tokenizer is used, this object can expose token-to-word and token-to-character relationships generated during preprocessing.

Character offsets

This is essential for highlighting predictions and for extractive QA, where token start/end predictions have to become exact character spans again.

Word alignment

Token classification uses this mapping to convert one label per word into a model label per relevant subtoken.

Sequence IDs

For paired inputs, sequence-alignment metadata can distinguish tokens belonging to the first sequence, second sequence and special tokens. QA uses this to identify which tokens belong to the context rather than the question when generating answer candidates.

Why token strings are not enough

Looking at decoded token strings and trying to infer source positions is unreliable. Fast tokenizers in the QA pipeline

Use offsets and overflow windows to recover answer text from contexts longer than the model limit.

─────

Extractive question answering does not generate an answer from scratch. A model scores possible start and end token positions inside a supplied context. After the model chooses promising positions, the system must map those token indices back to the exact character span shown to the user. Fast-tokenizer offset mappings provide that bridge.

Question and context are usually tokenized as a pair. When the context exceeds maximum sequence length, simple truncation could delete the answer. The QA pipeline therefore creates overlapping windows using overflow features and a stride. Each feature contains the question plus a chunk of context; overlap protects answers near chunk boundaries.

For each chunk, the model outputs start and end logits. Post-processing restricts candidates to valid context tokens, considers reasonable start/end combinations, scores candidate spans, and converts the winning token range through offsets into source text. The final answer's character start and end positions refer to the original context.

This lesson is a concrete demonstration of why tokenization metadata matters. Without offsets, a model may know which token positions are best, but the application cannot robustly reconstruct the exact user-visible answer.

QA starts with two coordinate systems

The QA model predicts token positions, but the user expects characters from the original context. The fast tokenizer is the bridge between those coordinate systems. Offset mappings associate each context token with its source character range.

Long contexts need overflow features

The question plus full context may exceed the model's maximum sequence length. Instead of discarding everything after the limit, tokenize with truncation of only the context, return overflowing tokens and use a stride so consecutive context chunks overlap.

One raw QA example can therefore produce several model features. Each feature repeats the question and contains a different context window.

Why overlap matters

Without stride, an answer that crosses exactly between two chunks could be split so neither chunk contains the complete answer. Overlap makes boundary regions appear in both neighboring features, increasing the chance that at least one feature contains the whole span.

Start and end logits

The QA head produces one start score and one end score per token. Inference considers high-scoring start/end combinations, rejects impossible pairs such as end-before-start or spans outside the context, and computes a score for remaining candidates.

The best candidate is still a token range at this stage.

Map back to source text

Use offset mappings for the selected start and end tokens to obtain the exact character boundaries in the original context. Slice the original string with those coordinates so punctuation, spacing and capitalization match what the user supplied.

Multiple windows

Every overflow feature can propose an answer. Post-processing compares candidates across all windows associated with the same original example. The raw model itself does not know that several features came from one context; that relationship is maintained by preprocessing metadata.

Normalization and pre-tokenization

─────

Normalization transforms raw Unicode text before tokenization. Depending on the tokenizer, this can include Unicode normalization, lowercasing, accent stripping, or whitespace cleanup. These choices change the symbols available to later stages, so they must match training and inference.

Pre-tokenization creates preliminary splits, commonly around whitespace and punctuation, before the subword model decides how to represent each piece. Some tokenizers encode spaces explicitly or use byte-level pre-tokenization rather than ordinary word splitting.

Normalization

Normalization transforms raw text before subword segmentation. A normalizer may apply Unicode normalization, lowercase letters, strip accents or standardize whitespace. These operations alter the symbol stream that the vocabulary model sees.

The tokenizer used at inference must perform the same normalization as the tokenizer used to learn/train model inputs. Changing normalization changes token boundaries and IDs.

Unicode normalization

Compatibility normalization can also change characters that look or behave similarly, so the choice is not semantically neutral for every application.

Pre-tokenization

Byte-Pair Encoding tokenization

Learn the merge-based algorithm used by many GPT-style tokenizers.

─────

BPE training begins from a base vocabulary of small symbols—characters or bytes depending on the variant. It counts adjacent symbol pairs in the corpus, merges a frequently occurring pair into a new token, updates the segmentation, and repeats until the target vocabulary/merge budget is reached.

The learned merge order becomes part of the tokenizer model. At tokenization time, text is normalized and pre-tokenized, then compatible merges are applied according to the learned rules. Frequent sequences become compact tokens while uncommon words can still be composed from smaller pieces.

Byte-level BPE begins from the 256 possible byte values. Because arbitrary Unicode text can be represented as bytes, this gives robust coverage and largely avoids a classic unknown-character problem. The trade-off is that some human characters may be represented by multiple bytes before merges learn useful higher-level pieces.

BPE should be remembered as iterative pair merging. It does not have to understand morphology; useful morpheme-like pieces emerge only when corpus frequencies make them advantageous.

BPE starts from small symbols

Byte-Pair Encoding begins with a base vocabulary of small units—characters in a simple derivation or bytes in byte-level BPE. The training corpus is represented as sequences of those units.

Count adjacent pairs

At each training step, count how often adjacent token pairs occur in the current segmentation. A pair that appears frequently is a candidate to become one new vocabulary token.

Merge and repeat

Select a high-frequency pair, add the concatenated piece to the vocabulary and replace occurrences of that pair in the training representation. Then recompute pair statistics and repeat until the vocabulary reaches the target size or merge budget.

The order of learned merges matters because later merges can build on pieces created earlier.

Encoding new text

To tokenize unseen text, start from the base units and apply learned merge priorities so frequent known combinations become larger pieces. Rare words remain decomposable because the base alphabet still provides coverage.

Byte-level BPE

Using bytes as the initial alphabet gives a fixed set of 256 possible byte values, so arbitrary Unicode text can be represented without a conventional unknown character. Human characters encoded as several bytes may initially look strange, but merges learn common byte sequences back into useful pieces.

GPT-2-style tokenization popularized this approach.

BPE intuition

BPE is a compression-like vocabulary algorithm. It spends vocabulary slots on recurring adjacent strings because doing so shortens the corpus representation. The pieces do not have to correspond to linguistically correct morphemes; any frequent sequence can become useful.

A small manual example

Imagine a corpus containing many forms of low, lower, and lowest. The initial representation might be characters. If l+o is frequent it can merge to lo, then lo+w to low, and later low+er if er has also become a piece. The final vocabulary reflects corpus frequency rather than a dictionary of whole words.

WordPiece tokenization

Understand why WordPiece looks like BPE at inference but learns pieces with a different scoring principle.

─────

WordPiece, associated with BERT-family tokenization, also builds a subword vocabulary but does not simply choose the globally most frequent adjacent pair at each step. The course explains the commonly reconstructed algorithm using a pair score that considers joint frequency relative to the frequencies of the individual pieces. This discourages merges that are common only because their components are individually ubiquitous.

Continuation pieces are often represented with a marker such as ## in BERT tokenizers. During encoding, a word is greedily decomposed into vocabulary entries, typically selecting the longest matching piece from the current position. If no decomposition exists in a WordPiece vocabulary with unknown-token behavior, the word may fall back to [UNK].

The original Google WordPiece training algorithm was not fully published, so the course is explicit that the training description is an informed reconstruction. The practical distinction to remember is: BPE is taught as frequency-based pair merges, while WordPiece uses a frequency-normalized merge scoring idea and longest-match tokenization.

How WordPiece differs conceptually

WordPiece also learns subword pieces, but the course presents a scoring rule that favors a pair when its joint frequency is large relative to the individual frequencies of its components. A pair composed of two extremely common pieces therefore needs stronger evidence than a pair whose parts are rare.

Pair score intuition

A simplified score is proportional to frequency(pair) / (frequency(left) * frequency(right)). This normalizes raw pair frequency and tends to favor combinations that form a particularly strong association rather than merely appearing often because each component is ubiquitous.

Continuation markers

BERT-style WordPiece vocabularies often mark non-initial word pieces with ##. The marker represents positional/tokenization structure; it is not literal source text. For example, one word may tokenize into an initial piece and one or more continuation pieces.

Longest-match tokenization

At encoding time, WordPiece commonly uses a greedy longest-match-first procedure. Starting from the beginning of a word, choose the longest vocabulary token that matches; then continue with the remaining substring using continuation forms.

If no valid decomposition can be found under a vocabulary that supports an unknown token, the word may become [UNK].

Original algorithm caveat

The exact original WordPiece training procedure was not fully published, so educational descriptions reconstruct the algorithm from known behavior. The practical takeaway is the contrast with BPE's straightforward frequency-based merging and WordPiece's normalized scoring/greedy encoding convention.

Unigram tokenization

Learn a probabilistic alternative that starts large and removes vocabulary pieces instead of building upward through merges.

─────

Unigram reverses the growth intuition of BPE. It begins with a relatively large candidate vocabulary. Each piece receives a probability in a simple language model over tokenizations. The training procedure evaluates which tokens can be removed with the smallest increase in corpus loss, removes a fraction, re-estimates probabilities, and repeats until the desired vocabulary size is reached.

A string can have multiple possible segmentations. Rather than following one deterministic sequence of merge rules, Unigram scores segmentations probabilistically and chooses a high-probability path, commonly with dynamic programming.

This makes the vocabulary objective fundamentally different from BPE even though both end with subword pieces. SentencePiece can use Unigram and is designed to work directly from raw text, which is particularly useful for multilingual settings where whitespace cannot be assumed to define word boundaries in the same way.

Start large, then prune

Unigram takes the opposite direction from BPE. Instead of beginning with tiny units and repeatedly adding merged pieces, it begins with a large candidate vocabulary capable of representing the corpus.

A probabilistic token model

Each vocabulary piece receives a probability. A tokenization of a string has a probability related to the product of probabilities of its chosen pieces. Different segmentations of the same word can therefore be compared probabilistically.

Best segmentation

Dynamic programming can find the highest-scoring segmentation without enumerating every possible tokenization explicitly. This is necessary because a string may have many overlapping candidate pieces.

Remove low-value tokens

Training estimates how much corpus likelihood would worsen if a candidate token were removed. Tokens whose removal hurts least are pruned, probabilities are re-estimated and the process repeats until the desired vocabulary size is reached.

The algorithm therefore optimizes a vocabulary by subtraction rather than building one exclusively through merges.

SentencePiece

SentencePiece is a tokenizer framework that can train Unigram or BPE models directly on raw text and can represent whitespace as part of the tokenization scheme. This is useful for languages where traditional space-delimited “words” are not a universal assumption.

Subword regularization

Because Unigram maintains probabilities over alternative segmentations, training systems can sometimes sample different valid tokenizations of the same text. This can act as a form of data augmentation, exposing a model to segmentation variability rather than one rigid decomposition.

Token classification

Align labels defined over words with model inputs defined over subword tokens.

─────

Named-entity recognition is a token-classification problem. A common BIO tagging scheme uses B-* for the beginning of an entity, I-* for continuation, and O for tokens outside entities. Raw datasets may supply one label per original word, but a Transformer tokenizer can split one word into several subtokens.

Fast tokenizer word_ids() tells which source word generated each model token. Special tokens map to no source word. During alignment, the first subtoken can receive the word's label while later subtokens are either assigned a continuation-compatible label or ignored, depending on the chosen training convention.

Cross-entropy losses in Transformers commonly ignore label value -100. Assigning -100 to special tokens and deliberately ignored subtokens keeps them from contributing to loss. DataCollatorForTokenClassification pads labels consistently with token sequences.

Evaluation usually reconstructs entity labels while excluding ignored positions and may use sequence-labeling metrics rather than naïve token accuracy. Entity-level precision/recall/F1 are more meaningful when boundary correctness matters.

The NER data shape

Named-entity datasets often store a list of original words and a parallel list of entity tags. BIO/IOB-style labels distinguish the beginning of an entity span from continuation tokens and outside tokens. For example, an organization may be represented by B-ORG followed by I-ORG tags.

Load and inspect labels

Class-label features can expose the mapping between integer IDs and tag names. Inspect the label set and a full example before tokenization so you know whether the raw unit is a word, character span or already-tokenized sequence.

Tokenize pre-split words

When a Dataset already supplies a list of words, call the tokenizer with the setting that tells it the input is pretokenized. The tokenizer can still split one word into several subword pieces, so the output length is generally not equal to the number of source words.

Align labels with `word_ids()`

For each token position, word_ids() identifies which original word generated it. Special tokens have no source word. Use this mapping to construct a label list with exactly the same sequence length as the model input.

What to do with subtokens

One common strategy labels the first subtoken of each word and assigns -100 to subsequent subtokens so the loss ignores them. Another strategy propagates labels, converting a B-* label into I-* for later pieces where appropriate. The choice changes the effective training objective and must be consistent with evaluation.

Why `-100` appears

PyTorch cross-entropy as used by Transformers commonly treats -100 as an ignore index. Special tokens and deliberately unscored subtokens can therefore occupy tensor positions without contributing to the loss.

Token-classification collator

DataCollatorForTokenClassification pads model inputs and the parallel label sequence together. A generic text collator that pads only token IDs would leave labels with inconsistent lengths.

AutoModelForTokenClassification adds one classifier over every token hidden state. Evaluation should ignore positions whose reference label is -100 and convert predicted/reference IDs back to tag strings for entity-aware metrics such as seqeval.

Entity-level F1 is usually more meaningful than raw token accuracy because correct span boundaries matter.

Inference and aggregation

At inference, subword token predictions have to be aggregated back into user-visible words/spans. Pipelines can perform common aggregation strategies, but custom applications should preserve offsets so highlighted entity spans correspond exactly to the original text.

Fine-tuning a masked language model

Adapt a pretrained encoder's language representations to a specialized domain before a downstream task.

─────

A masked language model learns by replacing or hiding selected input tokens and predicting the originals. If a general BERT-style checkpoint has not seen enough language from your domain, continuing that objective on unlabeled domain text can adapt representations before task-specific fine-tuning.

This is domain-adaptive pretraining, not ordinary classification fine-tuning. The labels are generated from the text itself, so large quantities of unlabeled in-domain text can be used. A data collator for language modeling can create masks dynamically during batching, exposing the model to different corrupted versions across epochs.

The strategy is useful when the domain distribution differs meaningfully—scientific papers, legal text, clinical text, internal support logs, and so on. It costs extra compute, so the benefit should be evaluated against simply fine-tuning the original checkpoint.

The broader lesson is that pretraining and fine-tuning form a continuum. You can insert an intermediate self-supervised adaptation stage when domain language is the missing piece.

Why continue masked-LM pretraining

A general encoder may not represent a specialized domain optimally. Continuing the same masked-language-model objective on unlabeled in-domain text adapts vocabulary usage and contextual representations before you train a downstream classifier or extractor.

This is often called domain-adaptive pretraining. It sits between initial pretraining and task fine-tuning.

Prepare domain text

The dataset does not require hand labels because the MLM objective generates its own targets. Clean the text enough that artifacts do not dominate the corpus, but preserve domain terminology and structures you actually want the model to learn.

Tokenize and group text

Tokenized documents may be concatenated and split into fixed-length blocks so the model receives efficient sequences. Very short fragments can waste batch space; excessively aggressive concatenation can erase useful document boundaries. Choose a block size consistent with the model's context limit and task needs.

Dynamic masking

A language-modeling data collator can randomly select mask positions each time examples are batched. Dynamic masking means the same raw sequence can present different prediction targets on different epochs, providing more varied supervision than permanently masking the dataset once.

The MLM corruption rule

Classic BERT-style masking does not simply replace every selected token with [MASK]. A masking policy can sometimes keep or replace selected tokens so the model does not rely exclusively on a special symbol that will never appear in downstream inputs. Use the collator implementation compatible with the desired objective.

Train the MLM head

AutoModelForMaskedLM projects token hidden states into vocabulary logits. Loss is computed only at selected/labelled positions, with non-target positions ignored. The model updates both backbone representations and language-model head during continued pretraining.

Evaluate adaptation

A lower MLM loss on in-domain validation text shows better prediction under that objective, but the real test is whether the adapted checkpoint improves downstream tasks. Domain adaptation adds a training stage, so compare against directly fine-tuning the original checkpoint rather than assuming it helps.

Push the adapted checkpoint

An adapted MLM checkpoint can be published to the Hub and then used as the starting point for later task fine-tuning. Document the domain corpus and adaptation objective in the model card because they meaningfully change the checkpoint's behavior and limitations.

Translation

Prepare a sequence-to-sequence problem where source and target are different languages.

─────

Translation naturally matches an encoder–decoder architecture. The encoder reads the source sentence and builds contextual representations. During training, the decoder receives shifted target information and learns to predict the next target-language tokens conditioned on both the encoder output and earlier target tokens.

The dataset therefore contains source–target pairs. Tokenization must respect the model's language conventions; multilingual models may require source/target language codes or prefixes. Labels are target token IDs, with padded target positions ignored in loss.

At inference the target is not available. The decoder generates autoregressively using a search/decoding strategy. This makes evaluation different from teacher-forced training. BLEU and related metrics compare generated translations with references, but human adequacy, fluency, terminology, and named-entity preservation can reveal failures that n-gram metrics miss.

Translation dataset structure

A translation dataset stores paired source and target strings, often inside a translation mapping keyed by language code. Inspect the available language directions and examples before preprocessing. Multilingual datasets may require selecting or filtering one language pair.

Checkpoint and language conventions

Seq2seq checkpoints can have language-specific requirements. Some multilingual tokenizers need source and target language codes; text-to-text models may use task prefixes. Follow the checkpoint's preprocessing convention rather than assuming every encoder–decoder accepts identical raw strings.

Tokenize source and target

The encoder input is the tokenized source sentence. Training labels are the tokenized target sentence. The tokenizer API can enter a target-text mode or accept a text_target argument so source and target are processed with the correct configuration.

Seq2seq data collator

DataCollatorForSeq2Seq pads encoder inputs and target labels and can prepare decoder inputs for compatible models. Target padding positions are replaced with an ignore index so loss is not computed on artificial pad tokens.

Teacher forcing during training

The decoder learns to predict each next target token while conditioned on the encoder output and earlier target tokens. During training, the known reference target provides those earlier positions (shifted appropriately). This is different from inference, where the model has to condition on its own generated prefix.

Generation for evaluation

Translation quality must be evaluated on generated text, not only teacher-forced loss. Trainer configurations for seq2seq tasks can call generate() during evaluation, decode the token IDs and pass strings to a metric.

BLEU

BLEU compares n-gram overlap between generated translations and one or more reference translations with a brevity penalty. It is useful for benchmark comparison but does not directly measure semantic adequacy, terminology correctness or naturalness in every case.

Always pair an automatic metric with representative examples when domain correctness matters.

Inference

At inference, tokenize a source sentence, call generate() with appropriate decoding settings and decode the target token IDs while skipping special tokens. Beam search or other decoding policies can alter quality/latency even though the model is unchanged.

Summarization

Train a seq2seq model to generate a shorter representation of a source document.

─────

Abstractive summarization has the same broad encoder–decoder mechanics as translation, but source and target are in the same language and the target is a compressed semantic representation rather than a translation. The model can generate words that do not occur verbatim in the source.

Input-length limits are a central practical constraint. If the source document is truncated, the summarizer cannot include information it never saw. Long-document systems may need chunking, hierarchical processing, long-context architectures, or retrieval rather than simply increasing max_length.

ROUGE measures overlap between generated and reference summaries and is useful for comparative experiments. It does not guarantee factual consistency. A generated summary can share many reference words and still misstate a relationship or number, so factuality and human-usefulness evaluation should accompany automatic overlap scores.

Summarization data

A summarization dataset contains a source article/document and a target summary. Inspect source-length distributions early; long documents can exceed the model's maximum context, which turns truncation policy into a central modeling decision rather than a minor tokenizer flag.

Preprocessing

Tokenize documents as encoder inputs and summaries as target labels. Text-to-text checkpoints such as T5 may use a task prefix that tells a generally trained model which transformation is required.

Set source and target maximum lengths separately because summaries are usually far shorter than articles.

Dynamic seq2seq batching

Use a seq2seq collator to pad sources and labels independently. Efficient batching can group similar lengths, but the essential requirement is that label padding be ignored by the loss.

Fine-tuning

A seq2seq model learns to generate the reference summary token by token conditioned on encoded source representations. Training loss measures reference-token prediction under teacher forcing; it does not directly measure factual consistency of free generations.

ROUGE

ROUGE measures overlap between generated and reference summaries, commonly using unigram, bigram or longest-common-subsequence variants. It rewards lexical similarity, which is useful for benchmarks but incomplete for abstractive summarization.

A hallucinated fact can coexist with high lexical overlap. Evaluate factual consistency and coverage separately when mistakes matter.

Generation length and decoding

Generation settings such as maximum new tokens, beam width, length penalty and repetition constraints shape summaries. Very short limits force omission; very generous limits may produce verbose or repetitive output. Tune them on validation examples rather than copying defaults blindly.

Long-document strategies

If important information is routinely truncated, consider chunked summarization, hierarchical summarization, long-context models or retrieval-based selection. Increasing tokenizer max_length beyond the model's actual position capacity does not create new context support.

Tokenized text is concatenated or chunked into fixed context windows. Overflow handling lets one long document produce multiple training sequences. Training a causal language model from random weights is dramatically more expensive than fine-tuning. It is justified when available pretrained checkpoints do not match the language/domain/tokenization/data requirements or when the goal is to study pretraining itself. The course uses a code corpus to expose the full pipeline at manageable scale.

Stream a large code corpus

A massive corpus does not need to be downloaded in full before inspection. Streaming lets you iterate files, filter for languages/libraries of interest and estimate the usable data distribution.

The course example focuses on code related to selected Python libraries. This creates a narrower training distribution and demonstrates a general pretraining lesson: corpus curation defines model behavior. “More tokens” is not automatically better if most tokens are irrelevant or low quality.

The toy workflow is structurally the same as large-model pretraining: collect/clean tokens, choose a tokenizer and architecture, pack sequences, optimize next-token likelihood over huge compute, evaluate and checkpoint. Question answering

Train an encoder to point to an answer span inside a context.

─────

Extractive QA datasets typically store a question, a context string, and answer text with character start positions. The model, however, predicts token indices. Preprocessing must therefore map each character answer span to the tokenized context using offset mappings.

Long contexts create multiple tokenized features for one raw example. Overflow mapping records which source example produced each feature, and stride creates overlapping windows. During training, the correct feature receives token-level start_positions and end_positions; a window that does not contain the answer needs an explicit no-answer/default treatment appropriate to the dataset/model setup.

At evaluation/inference, the model emits start and end logits for every feature. Post-processing combines plausible start/end indices, rejects spans outside the context or with invalid length/order, converts token positions back to character offsets, and selects the highest-scoring candidate across windows.

This task illustrates a recurring ML pattern: the loss is computed in model coordinate space, while the final output must be mapped back into human coordinate space.

Extractive versus generative QA

The lesson focuses on extractive question answering: the model receives a question and a context and must identify the answer as a span already present in that context. Encoder models such as BERT are strong for factoid extraction. Open-ended explanation questions typically require a generative formulation instead.

The SQuAD schema

SQuAD provides an id, article title, context, question and answers. The answer object stores answer text plus one or more answer_start character positions. Training examples have a canonical answer; validation can include multiple acceptable surface forms for scoring.

Character offsets are the raw labels

The source dataset labels answers in character coordinates because that is natural for annotated text. The model does not operate on character positions—it operates on tokens. Preprocessing must therefore convert character start/end positions into token indices.

Tokenize question and context as a pair

A BERT-style input contains the question and context separated by special tokens. The question should generally remain intact while long contexts are truncated/chunked. Fast tokenization is required because offset mappings are needed for label conversion and later answer reconstruction.

Long context and sliding windows

Set a maximum sequence length, truncate only the context and request overflowing features with a stride. One raw example can become several features. The stride preserves overlapping context so an answer near a chunk boundary can appear completely in at least one feature.

Overflow-to-sample mapping

When a batched tokenizer creates multiple features from one input example, metadata maps each produced feature back to its source example. This is needed to retrieve the correct raw answer annotations while computing labels.

Sequence IDs identify context tokens

The tokenized feature contains question tokens, context tokens and special tokens. Sequence IDs tell preprocessing which token positions belong to the context. Answer labels must never point into the question or a special token.

Convert an answer to token start/end

Take the annotated character start and end, examine context-token offset mappings and find the token whose span contains the answer start and the token whose span contains the answer end. Those indices become start_positions and end_positions training labels.

If a particular overflow feature does not contain the annotated answer, assign the model's designated no-answer/CLS-style position according to the preprocessing recipe.

Training features versus validation features

Training preprocessing can discard some metadata once token labels have been constructed. Validation preprocessing must preserve example IDs and context offsets because post-processing later needs to map model logits back to original examples and strings.

Load the QA model

AutoModelForQuestionAnswering attaches a span head that produces start and end logits for every token position. The training loss compares these logit distributions with the labelled start/end token indices.

Post-process logits

For each feature, choose several high-scoring start and end positions rather than greedily selecting one of each independently. Combine candidates, reject end-before-start spans, spans that are too long and indices that are not context tokens, then score remaining spans by the sum of start/end logits.

Combine overflow features

Several features can correspond to the same raw context. Group candidate answers by original example ID and select the highest-scoring valid span across its features. This is application post-processing around the model, not a learned operation inside BERT.

Map token candidates to characters

Offset mappings turn a chosen start token's beginning offset and end token's ending offset into source character indices. Slice the original context to recover the exact answer text.

SQuAD metrics

Extractive QA commonly reports Exact Match and token-level F1. Exact Match requires the normalized prediction to equal an acceptable reference. F1 gives partial credit for token overlap. When several references are accepted, scoring uses the best match.

These metrics measure span correctness, not the quality of explanations beyond the supplied context.

Trainer evaluation

Because metrics require nontrivial post-processing from start/end logits to strings, QA evaluation is more complex than simple classification. The evaluation pipeline has to retain validation metadata, run predictions, reconstruct answers and then call the metric.

Accelerate implementation

The same training can be implemented in a manual PyTorch/Accelerate loop. The hard part remains data and post-processing rather than the optimizer: once batches contain valid start/end labels, the gradient loop is ordinary Transformer fine-tuning.

Debugging the training pipeline

Disassemble Trainer into inspectable stages until the first wrong assumption is found.

─────

Start with the dataset that Trainer actually receives. Inspect a few rows and decode token IDs. Verify the expected columns exist and that labels use the intended IDs. A frequent failure is configuring num_labels inconsistently with the dataset labels or passing raw, untokenized columns to a collator/model that expects tensors.

Next, run the data collator on a handful of examples and print every tensor's shape and dtype. Then move the batch to CPU and call the model directly. CPU execution can produce clearer synchronous errors than some CUDA failures, and it removes GPU memory/device complications from the first diagnosis.

If the forward pass works, inspect outputs.loss and outputs.logits. Only then test loss.backward(), optimizer steps, evaluation, and finally Trainer orchestration. This ordering narrows the bug from 'training does not work' to a single failing boundary.

Inspect Trainer's dataset

Look at the exact dataset object passed to Trainer, not the raw object you think you transformed. Print a few rows and verify required fields exist. Decode input_ids to make sure text and pair ordering are correct.

Inspect the collated batch

Call the data collator manually on a few examples. Print keys, tensor shapes and dtypes. Check that labels are padded/aligned and that batch dimensions match across fields.

Move the smallest case to CPU

A CPU forward pass removes CUDA memory and asynchronous-kernel complications. If the model fails synchronously on CPU, the error message often points much closer to the true bad index or shape.

Run one forward pass

Call model(**batch) without Trainer. Inspect loss and logits. If this fails, the bug is in data/model compatibility rather than Trainer's optimization orchestration.

Check label ranges and `num_labels`

Classification labels must be valid indices for the configured number of labels. A dataset containing class ID 4 with a head configured for four classes (0..3) can trigger a low-level indexing error, including opaque CUDA assertions.

If forward works, call loss.backward(). Failures here point toward autograd, custom operations, mixed precision or numerical issues rather than basic input structure.

Add optimizer and scheduler

Once forward/backward work, perform one optimizer update. Then add evaluation. Only after each component works independently should you reintroduce Trainer, mixed precision, multiple GPUs or callbacks.

GPU kernels can report an error after the operation that caused it. Reproducing on CPU or forcing synchronous execution during debugging can make the failing operation clearer. Do not assume the line where CUDA finally reports the error is the original bug.

Chat Templates

Treat conversation serialization as part of the model contract.

─────

A chat application may store messages as structured objects such as {role: 'user', content: ...}. The language model does not directly consume dictionaries; it consumes tokens. A chat template serializes those structured messages into the special tokens and delimiters expected by the instruct model.

Different model families encode roles and message boundaries differently. ChatML-style models may use explicit start/end tokens for system, user, assistant, and tool roles; other families use instruction delimiters or different special tokens. Two conversations that look identical in a UI can therefore become very different token sequences.

tokenizer.apply_chat_template() centralizes this model-specific serialization. The template is commonly stored in tokenizer configuration, so using the tokenizer associated with the checkpoint helps prevent formatting drift. A wrong template can substantially degrade instruction following because the model is seeing a sequence structure different from the one used during adaptation.

Templates also extend beyond simple text turns. Tool calls, tool results, multimodal content, function calling, and multi-turn history can introduce model-specific structures. Validate message schemas and watch context length: the template itself consumes tokens in addition to message content.

The course distinguishes base and instruct models here. A base model is optimized primarily for continuation; an instruct variant has been further trained on conversational/instruction data represented through a particular template.

Structured conversation data

Applications commonly store a conversation as a list of messages, each with a role and content. Roles can include system, user, assistant and tool. This structure is convenient for software, but the causal LM ultimately consumes one token sequence.

What a chat template does

A chat template serializes the structured messages into model-specific text/special tokens. It inserts role delimiters, message boundaries and often a marker indicating that the assistant should begin generating next. The result is then tokenized normally.

Templates differ across checkpoints

There is no universal chat syntax. One instruct family may use <|user|>-style markers, another instruction brackets, another begin/end-of-turn tokens. A model trained on one structure can perform noticeably worse if prompted with another, even when the visible English content is identical.

Base versus instruct checkpoints

A base model is primarily pretrained for continuation and may not have a chat template at all. An instruct model has additional post-training that teaches it to respond to role-formatted instructions. Loading the instruct tokenizer normally gives access to the expected template.

Use `apply_chat_template`

Rather than hardcoding delimiters in application strings, call the tokenizer's template helper with structured messages. It can return either formatted text or token IDs. add_generation_prompt=True (when applicable) appends the model-specific marker that says an assistant response should follow.

System messages

A system message provides high-level behavioral context in model families trained to recognize that role. It is not a privileged security mechanism by itself; it is still tokens in the context. Application-level enforcement is needed for constraints that must not be bypassed.

Multi-turn conversations

Every prior turn included in the message list consumes context tokens. The template repeats role/boundary tokens around turns, so conversation history has overhead beyond the visible words. Long chats need truncation, summarization or retrieval policies that preserve important instructions and recent context.

Tool messages

Tool-capable checkpoints may serialize tool definitions, calls and tool results with additional schema. Follow the checkpoint's documented template because the model may have learned a very specific JSON or token convention for calling and observing tools.

Multimodal templates

For vision-language or other multimodal models, a message may contain structured content parts rather than one text string. A processor/chat template can insert placeholders corresponding to image/audio embeddings. The conceptual role is still serialization of application structure into the model's expected input representation.

If SFT examples are formatted one way but production inference uses a different template, the application introduces avoidable distribution shift. Store the template with the tokenizer artifact and test exact formatted inputs during evaluation.

Fine-Tuning with SFTTrainer

Adapt a causal model to desired instructions, domain language, or output behavior using supervised examples.

─────

Supervised Fine-Tuning (SFT) trains on examples of behavior you want the model to reproduce: prompts/conversations paired with target assistant responses. It is not automatically the first solution. If a capable instruct model already meets the requirement with prompting, SFT adds data, compute, evaluation, and maintenance cost without guaranteed benefit.

The course highlights two strong reasons for SFT: template/output control and domain adaptation. Examples can teach a consistent schema, tone, or conversational pattern, and they can expose the model to specialized terminology and task behavior that prompting alone does not reliably elicit.

Dataset quality dominates. Each example should have coherent input and target output and should be serialized with the correct chat template. Duplicates, contradictory responses, incorrect facts, and low-quality synthetic data are supervision too—the model is explicitly trained to imitate them.

SFTTrainer in TRL handles the causal-LM training workflow around conversational or formatted datasets. Configuration includes training duration (num_train_epochs or max_steps), per-device batch size, gradient accumulation, learning rate and warmup, logging, evaluation, and checkpoint cadence. Gradient accumulation creates a larger effective batch without storing that entire batch in memory at once.

Packing can combine several short examples into one model-length sequence to improve token utilization. It changes how many examples fit into each optimizer step, so monitor effective training exposure rather than assuming one packed sequence equals one original example.

Training loss should be interpreted alongside validation loss and qualitative generations. Falling train loss with rising validation loss signals overfitting; almost no improvement can indicate optimization or data/task problems; extremely low loss plus verbatim-like behavior can indicate memorization. A model can also have reasonable loss while learning the wrong response format, so sample generations during training.

When SFT is appropriate

First try a capable instruct checkpoint with prompting. SFT is justified when prompt-only behavior is persistently unreliable, domain conventions are poorly represented, output schemas must be consistent, a smaller specialized model is desirable, or repeated long prompts would be more expensive than learning the behavior into weights.

Template and style control

Supervised examples can teach a model to respond in a particular conversation pattern, tone or structured output. This is stronger than merely writing “always output JSON” in one prompt because the desired behavior appears repeatedly in the optimization targets.

Domain adaptation through SFT

SFT can expose an instruct model to domain-specific tasks and terminology, but distinguish this from continued language-model pretraining. SFT teaches input-to-response behavior from labeled/instruction examples; domain-adaptive pretraining teaches general next/masked-token modeling on unlabeled domain text.

Dataset formats

TRL can work with conversational datasets containing message lists or with prompt/completion/text formats depending on configuration. Normalize the dataset so every example has one unambiguous source and target semantics. Mixed schemas create silent formatting errors.

Validate conversations

Check that roles alternate as intended, assistant targets are present, content is non-empty and template rendering produces exactly the expected special tokens. Remove duplicate or contradictory examples. A model is trained to imitate errors just as enthusiastically as desired behavior.

Train/validation split

Keep a validation set representing the same use case but not duplicated/paraphrased copies of training examples. If examples come from conversations or documents, split by a higher-level source identifier when necessary to avoid leakage.

Choose training duration

SFT often needs fewer epochs than small classic datasets because LLMs begin from highly capable weights and examples can be long. Too little training fails to move behavior; too much can overfit wording, reduce generality or cause catastrophic shifts. Monitor validation and sample generations.

Batch size and gradient accumulation

Long sequences make per-device batches small. Gradient accumulation lets several micro-batches contribute to one optimizer update, increasing effective batch size without requiring all activations to fit simultaneously.

Effective batch depends on per-device batch, accumulation steps and number of parallel processes/devices.

Learning rate

LLM fine-tuning commonly uses a much smaller learning rate than training a small network from scratch. The exact range depends on full fine-tuning versus adapters, model size and data. An excessive rate can rapidly damage pretrained behavior.

Warmup and scheduler

Warmup gradually raises the learning rate during early steps before the main schedule. This can stabilize optimization while newly introduced gradients/adapters settle. Record the scheduler because two runs with the same nominal learning rate can behave differently under different schedules.

Logging, evaluation and checkpoints

Set evaluation and save cadence so you can see whether validation improves and recover a useful earlier checkpoint. Log learning rate, loss and, when possible, generated samples or task-specific validation metrics.

SFTTrainer

SFTTrainer combines Transformers/TRL training infrastructure with language-model-specific dataset formatting and packing support. It is still executing supervised causal-LM optimization: target assistant tokens contribute to loss according to the configured dataset/template behavior.

Packing

When individual examples are much shorter than the model context, packing places several examples into one sequence so fewer padding tokens consume compute. This can substantially improve token throughput.

Packing caveats

Packed examples require correct attention/loss boundaries so one example does not accidentally become semantic context for another in a way the trainer did not intend. Also reason about how many original examples appear per optimizer step; sequence count no longer equals example count.

Formatting functions

If the source dataset is not already in the trainer's expected conversational/text format, a formatting function can convert records into the serialized training representation. Keep this deterministic and test it on several examples before training.

Completion-only loss

For instruction data, you may want loss only on assistant completion tokens rather than teaching the model to reproduce the user prompt. Masking prompt tokens changes which positions contribute gradients. The correct policy depends on the trainer/version and task design.

Healthy loss pattern

Training and validation loss should usually fall early. If both stay flat, check formatting, labels/masking, learning rate and whether trainable parameters actually exist. If training falls while validation rises, overfitting is beginning.

Memorization

Very low loss and near-verbatim reproduction of training responses may indicate memorization, especially on small datasets. Test semantically similar but unseen prompts and measure whether the model generalizes the behavior rather than recalling exact strings.

Evaluate behavior, not only loss

A lower SFT loss does not guarantee better instruction following or factuality. Generate outputs on a fixed validation prompt suite and score format compliance, task correctness and failure cases. Chapter 11.5 expands this into a layered evaluation strategy.

LoRA (Low-Rank Adaptation)

Reduce the number of trainable parameters by learning low-rank updates instead of modifying every base weight.

─────

Full fine-tuning updates every selected model parameter and stores optimizer state for those parameters, which becomes expensive for large LLMs. LoRA freezes the original weight matrix and represents its learned update with two much smaller matrices. If a weight W would normally receive a dense update ΔW, LoRA approximates that update as B @ A with rank r much smaller than the full matrix dimensions.

The base computation becomes conceptually W x + scale · B(Ax). Only the adapter matrices are trained. Rank r controls adapter capacity; lora_alpha scales the adapter contribution; dropout can regularize the adapter path; target_modules chooses which projections receive adapters. Attention projections are common targets, but the best selection depends on architecture and task.

PEFT manages these adapters so the base checkpoint and task adapter can be saved separately. This is operationally useful: one base model can serve several small adapters, and publishing an adapter is far smaller than publishing another full copy of the model.

QLoRA goes further by loading the frozen base model in a quantized representation while training LoRA adapters in suitable precision. That can greatly reduce memory needs. Quantization is a representation/compute trade-off, while LoRA is a trainable-parameter trade-off; the two techniques solve related but distinct resource problems.

After training, an adapter can remain separate or be merged into base weights for a simpler single-model inference artifact. Merging reduces adapter-routing complexity but removes the convenience of swapping multiple adapters against one frozen base.

Full fine-tuning cost

Updating every model parameter requires gradients plus optimizer state for a very large weight set. Memory during training can therefore be several times the inference weight footprint, before activations and temporary buffers are counted.

The low-rank hypothesis

LoRA assumes the useful weight update for a downstream task can be approximated in a much lower-dimensional subspace than the full dense matrix. Instead of learning every element of a dense update ΔW, it learns two thin matrices whose product has rank at most r.

The adapter equation

For a frozen linear weight W, LoRA computes the base output Wx plus a trainable update proportional to B(Ax). If W is d_out × d_in, the dense update would contain d_out*d_in parameters. LoRA uses roughly r*(d_in+d_out) for that module, which is much smaller when r is small.

Rank `r`

Rank controls adapter capacity. Larger rank gives the update more degrees of freedom but increases trainable parameters and optimizer memory. More is not automatically better; choose rank based on task complexity, dataset size and validation results.

Alpha scaling

lora_alpha scales the low-rank update, commonly together with rank. It affects the effective magnitude of adapter contributions relative to the frozen base path. Treat it as an optimization/capacity hyperparameter rather than a cosmetic constant.

LoRA dropout

Dropout on the adapter path can regularize small datasets. Its usefulness depends on data size and whether other regularization is present. A zero value is common in some large instruction-tuning recipes.

Target modules

LoRA is inserted into selected linear projections. Attention query/value projections are common targets; many LLM recipes adapt query, key, value, output and MLP projections. Module names differ by architecture, so inspect the model rather than copying a target list blindly.

PEFT integration

The PEFT library wraps a base Transformers model with adapter modules, exposes trainable-parameter counts and saves adapter weights/configuration separately. This makes one base checkpoint reusable with many small task adapters.

Adapter checkpoints

Saving only the adapter can reduce storage from many gigabytes to a much smaller artifact. Reloading requires the compatible base checkpoint plus adapter configuration/weights. Document the exact base revision.

Merging

For deployment, adapter weights can be mathematically merged into the corresponding base weights, producing an ordinary model without separate adapter operations. This simplifies serving but removes easy adapter swapping and creates another full-size checkpoint.

QLoRA

QLoRA keeps the frozen base model in a low-bit quantized representation while training LoRA adapters in a higher precision suitable for optimization. Quantization reduces base-weight memory; LoRA reduces trainable/optimizer state. These are complementary techniques.

What QLoRA does not remove

Activations, KV/runtime buffers and generated sequences still consume memory. A quantized base does not make arbitrary sequence lengths or batch sizes free. Measure peak training memory for the actual context and gradient-checkpointing configuration.

Compare with full fine-tuning

LoRA often preserves much of full fine-tuning quality for instruction/domain adaptation, but the result is task-dependent. If the desired behavior requires broad changes across representations, full tuning or larger/more-targeted adapters may perform better. Evaluation, not ideology, decides.

Evaluation

Measure the behaviors your application needs instead of assuming one benchmark summarizes an LLM.

─────

General benchmarks are useful because they provide standardized comparisons. The course surveys suites covering broad knowledge, truthfulness, complex reasoning, mathematics, code generation, and instruction following. Their strength is comparability; their weakness is that benchmark distributions may not match your users, and public benchmarks can become contaminated by training data.

LLM-as-a-judge evaluation uses another model to score or compare outputs. It scales subjective evaluation more cheaply than humans, but the judge introduces its own bias, position preferences, style preferences, and model-family correlations. Pair it with calibration or human review for important decisions.

Arena-style evaluation collects pairwise preferences from users comparing outputs from models. This captures perceived quality under natural prompts but mixes many user goals and can favor presentation style over domain correctness.

The most important layer is a custom evaluation suite built from real requirements: representative user queries, edge cases, schema adherence, hallucination-sensitive cases, refusal/safety behavior where relevant, and domain-expert examples. Keep this set versioned and separate from training data.

A robust evaluation stack combines deterministic checks where possible, benchmark tasks, qualitative/human/domain review, and controlled online A/B testing when deployment permits. The metric should correspond to the actual cost of errors.

Why one benchmark is insufficient

LLMs are general systems with many failure modes. A benchmark can measure one distribution while your product cares about another. Good evaluation layers standardized benchmarks, task-specific tests, qualitative review and, when appropriate, real-user comparisons.

General knowledge benchmarks

Knowledge-oriented suites probe recall and reasoning across academic or factual domains. They make model comparison convenient but are vulnerable to dataset contamination and may overweight trivia relative to an application.

Reasoning and mathematics

Math/reasoning benchmarks provide questions with verifiable answers and sometimes structured solution requirements. Exact-answer scoring is attractive, but it can miss whether the reasoning is valid or whether an answer was guessed through shortcut patterns.

Code evaluation

Code benchmarks can run generated code against unit tests. Execution provides an objective signal, but the benchmark environment and hidden tests define what “correct” means. Security and resource isolation are essential when executing model-generated code.

Instruction following

Instruction-following evaluations test whether a model respects explicit constraints such as format, length, included/excluded content or multiple simultaneous requirements. These can reveal regressions that broad knowledge benchmarks miss.

LLM-as-a-judge

A judge model can rate or compare responses using a rubric. This scales evaluation and can score qualities difficult to express with exact metrics, but judge models have biases: position effects, verbosity preferences, self/model-family preference and sensitivity to rubric wording.

Pairwise preference

Instead of assigning an absolute score, compare two outputs for the same prompt and ask which is better. Pairwise judgments are often easier for humans and judge models. Aggregate comparisons can produce rankings such as arena-style leaderboards.

Human evaluation

Humans remain important for nuanced usefulness, domain correctness and safety. Define rubrics and provide representative prompts. Expert review is necessary when correctness depends on specialized knowledge that a generic crowd or judge model cannot reliably assess.

Custom evaluation suite

Build a versioned set from real user queries, historical failures, edge cases, adversarial/format cases and high-cost errors. Keep it separate from training data. This is usually the evaluation layer most correlated with product success.

Deterministic checks

When outputs have a schema, use parsers and assertions. Verify JSON validity, required fields, allowed values, citations or regex constraints automatically. Do not spend judge-model tokens checking something a deterministic parser can decide exactly.

Factuality and grounding

If the application answers from supplied evidence, test whether claims are supported by that evidence, not only whether the prose is plausible. Retrieval quality and generator grounding can be measured separately.

Safety and refusal behavior

Where relevant, evaluate both unsafe compliance and excessive refusal. A model that refuses harmless requests can be as unusable as one that fails to refuse dangerous ones. Test against the application's actual policy rather than one generic score.

Online A/B tests

After offline gates are passed, controlled online experiments can measure user success, corrections, latency and cost under real traffic. Online metrics should not be the first place you discover severe correctness or safety failures.

Evaluation after fine-tuning

Always compare the adapted model against the exact base/instruct baseline under the same prompts and decoding settings. Fine-tuning can improve the target behavior while degrading unrelated capabilities. Measure regressions intentionally.

Introduction

Why reasoning-oriented post-training focuses on generated trajectories and rewards rather than only imitating supervised answers.

─────

Supervised fine-tuning teaches a model to imitate target responses. Reinforcement-learning-style post-training instead samples model outputs and assigns reward according to desired properties. The optimization signal can therefore prefer one generated reasoning trajectory over another even when neither was supplied as an exact supervised target.

Reasoning tasks such as mathematics and code are attractive because correctness can sometimes be verified automatically. A reward based on a final numeric answer or executable tests is cheaper and less ambiguous than asking humans to score every reasoning trace. The challenge is designing rewards that encourage the intended reasoning rather than shortcuts.

This chapter uses DeepSeek-R1 and GRPO as the main conceptual path, then shows how the objective is implemented with TRL and resource-efficient tooling.

From imitation to reward optimization

SFT tells a model “produce responses like these targets.” Reinforcement-learning-style post-training lets the model generate several behaviors and supplies a scalar signal saying which outcomes are better. The model can therefore discover response trajectories that were not explicitly provided as target strings.

Why reasoning tasks fit

Math and code often have verifiable final outcomes: numeric answers, symbolic checks or unit tests. That makes it possible to assign reward automatically at large scale. The reward can encourage successful reasoning without requiring a human-written chain of thought for every prompt.

The central danger

The optimizer maximizes the reward function you implement, not the intention behind it. If a shortcut raises reward, training can learn the shortcut. Reasoning post-training is therefore as much a reward-design and evaluation problem as an optimizer problem.

Reinforcement Learning on LLMs

Translate agent/action/reward/policy concepts into token-generation training.

─────

In reinforcement learning, a policy selects actions based on a state and receives rewards from an environment. For an LLM, the policy is the model's conditional token distribution, the state contains the prompt and generated prefix, and a generated completion can be treated as a sequence of actions. A reward function scores the resulting behavior.

Unlike supervised learning, the target is not always a fixed reference sequence. The model samples behavior from its current policy, observes reward, and updates probabilities so higher-reward behavior becomes more likely. This creates an exploration problem: if the model never samples a useful strategy, the reward cannot reinforce it.

RLHF adds human preference information. One common pipeline collects comparisons between model responses, learns a reward/preference model, then optimizes the language model against that signal while constraining it from drifting too far from a reference policy. Other preference-optimization methods change the details but pursue the same broad alignment goal.

Reward specification is dangerous to treat casually. The optimizer targets the score you implement, not the intention in your head. If a reward can be increased through a formatting exploit, excessive verbosity, or another shortcut, training may discover it. This is reward hacking and is why verifiable, carefully tested rewards are valuable.

Agent, environment and state for an LLM

In the RL vocabulary, the policy is the language model. The prompt and generated prefix form the state/context. Tokens are actions, and a completed response is a trajectory or rollout. The environment/reward function evaluates that trajectory.

Policy

A policy maps a state to a probability distribution over actions. For a causal LM, that is literally the next-token distribution produced by softmax over vocabulary logits. Sampling from the policy generates a trajectory token by token.

Reward

A reward function maps generated behavior to a scalar. It may check exact correctness, execute code, validate a format or call a learned preference model. The reward need not be differentiable because policy-gradient methods use sampled outcomes to change action probabilities indirectly.

Exploration

The model has to sample candidate behaviors before the reward can identify good ones. If generation is completely deterministic and the current strategy is poor, learning has little behavioral diversity to compare. Sampling configuration therefore affects the data produced for RL updates.

Credit assignment

A final reward evaluates a whole sequence, but the model contains probabilities for every generated token. Policy-gradient objectives use the log probabilities of sampled actions so a positive advantage increases probability of the trajectory's actions and a negative advantage decreases it, subject to the chosen estimator and constraints.

RLHF preference data

Traditional RLHF often collects pairs of responses with human preferences. A reward model is trained to predict those preferences, then the policy is optimized to obtain high reward while staying reasonably close to a reference policy.

Reward model

A learned reward model converts qualitative preference data into a scalar signal that can score many new responses cheaply. It can also be exploited: its biases and blind spots become part of the optimization objective, so separate evaluation is required.

Reference policy and KL control

Without a constraint, the policy can move aggressively toward quirks that maximize the reward model. A KL penalty discourages large divergence from a reference model, preserving useful language behavior and reducing reward hacking.

PPO intuition

PPO-style language-model RL uses a policy plus a value/critic estimate to compute advantages, then clips policy updates so one batch cannot change probabilities too drastically. This critic/value component is one piece GRPO later avoids.

RL versus preference optimization

Not every alignment method performs explicit online RL rollouts. Direct preference-optimization methods can train from preference pairs with supervised-looking objectives. The course focuses here on RL concepts because GRPO samples groups of responses and optimizes rewards directly.

Reward hacking

If a reward gives points for including a phrase, the model may repeat the phrase; if length correlates with judge preference, responses may become unnecessarily long. Test reward functions against adversarial candidate outputs and monitor qualitative behavior throughout training.

Advanced Understanding of GRPO in DeepSeekMath

Derive the intuition behind group-relative advantages, clipped policy updates, and KL control.

─────

For each prompt q, GRPO samples a group of G completions from the policy. A reward function assigns each completion a scalar score. Because the completions share the same prompt, their rewards can be normalized within the group to create relative advantages: a response better than the group average receives positive advantage; a worse response receives negative advantage.

A simplified group-relative advantage is A_i = (r_i - mean(r)) / (std(r) + ε). This removes the need for a separate learned value model to estimate a baseline for every state. The group itself provides a local baseline. The price is generation compute: each prompt requires multiple completions.

The policy update compares the probability of sampled tokens under the current policy with the probability under the policy used to generate them. A probability ratio expresses how much the new policy has changed. Clipping limits the incentive for an excessively large single update, borrowing the stability idea used in PPO-like objectives.

A KL-divergence term or related reference constraint discourages the updated policy from moving too far from a reference model. This matters because aggressively maximizing a narrow reward can destroy useful language behavior or exploit imperfections in the reward.

GRPO therefore balances three forces: relative reward advantage says which sampled responses should become more or less likely; clipping controls update magnitude; KL control keeps the policy near a reasonable reference distribution.

Why GRPO uses groups

For one prompt, GRPO samples several completions from the current/old policy. Because all completions answer the same prompt, their rewards are directly comparable. The group supplies a local baseline: which responses did better or worse than their siblings?

Group-relative advantage

A simplified advantage normalizes each reward by the group's mean and standard deviation: A_i = (r_i - mean(r)) / (std(r) + eps). A completion above the group average gets positive advantage; one below average gets negative advantage.

This removes the need to train a separate value network to estimate a baseline for the prompt.

Why normalization helps

Raw reward scale can vary between prompts. Group normalization focuses the update on relative quality among completions for the same question. It also means a group with identical rewards provides little useful ranking signal.

Token probability ratio

The sampled completion was generated under an older/frozen snapshot of the policy. During optimization, compute the likelihood of those same sampled tokens under the updated policy and compare it with the old likelihood. The ratio indicates how much the new policy is changing probability of the observed action.

Clipped objective

If the ratio grows or shrinks too far, a clipped surrogate objective limits the benefit of pushing that sample even more aggressively. This is a stability idea inherited from PPO-like optimization: improve the policy, but avoid huge one-batch probability jumps.

Positive and negative advantage

For a positive-advantage completion, the objective encourages raising its likelihood, up to clipping effects. For a negative-advantage completion, it discourages the sampled trajectory. Because the loss is built from token log probabilities, the signal is distributed through the generated sequence.

KL penalty

A reference model provides another anchor. KL divergence measures how the current policy's distribution differs from that reference, and a penalty discourages excessive drift. The coefficient balances exploiting reward against preserving base behavior.

No critic/value model

PPO-style RL commonly trains a value function to estimate expected return. GRPO's group-relative baseline avoids that additional model/head, reducing memory and training complexity. It does not make generation cheap: each prompt still needs multiple completions.

Group size

More completions can give a richer estimate of relative performance but multiply generation cost. Too-small groups may provide noisy comparisons; too-large groups reduce how many distinct prompts fit in a fixed compute budget.

Reward variance

If every completion receives the same reward, normalized advantages collapse toward zero and the prompt provides little learning signal. Monitor group reward standard deviation. Low variance can mean the task is too easy, too hard or the reward is insufficiently discriminating.

Sequence-level reward and token-level update

GRPO often assigns one reward to the whole completion, yet the policy objective operates on probabilities of its tokens. This is a coarse credit-assignment mechanism: every token in a successful trajectory is reinforced according to the sequence advantage, even though some tokens may be irrelevant.

Importance sampling intuition

Using the probability ratio lets several optimization steps reuse trajectories sampled by an older policy while correcting for the fact that the new policy distribution has changed. Clipping limits how far that correction is trusted.

The compute bottleneck

The optimizer is not the expensive part. Autoregressively generating G completions for each prompt dominates wall-clock cost. Faster inference engines, shorter completions and careful batching are therefore central to practical GRPO.

Implementing GRPO in TRL

Translate the GRPO objective into a practical training configuration.

─────

TRL's GRPOTrainer needs a model/policy, a dataset of prompts, training configuration, and one or more reward functions. The trainer generates multiple completions per prompt, evaluates them with the reward functions, computes the group-relative training signal, and applies policy updates.

num_generations controls group size. Larger groups provide more within-prompt comparisons and may stabilize relative ranking, but generation cost and memory rise. Maximum prompt/completion lengths also directly affect resource use.

Reward functions should accept the generated outputs in the structure expected by the trainer and return numeric scores. For mathematics, code, or strict formats, deterministic verifiers can often supply stronger supervision than a vague style judge. Multiple reward functions can be combined, but their scales and incentives need inspection.

Monitor reward mean, reward spread/standard deviation, KL behavior, completion length, and task success. A rising reward with collapsing diversity or bizarre formatting may indicate reward exploitation rather than genuine improvement.

Prompt dataset

Unlike SFT, a GRPO training dataset can contain prompts without one fixed target response. The trainer samples completions from the policy during training. Include any ground-truth fields needed by reward functions, such as the correct numeric answer or tests.

Reward functions

A reward function receives generated output plus relevant example metadata and returns a numeric score. Keep it deterministic and verifiable where possible. Unit tests, exact symbolic answers and schema validators provide clearer signals than a vague learned judge.

Multiple rewards

Several reward functions can score different properties, such as correctness and format. Their scales and weights define the actual optimization target. Log components separately so a high total reward cannot hide collapsing correctness behind an easy format reward.

GRPOConfig

Training configuration includes learning rate, batch/prompts per step, num_generations, maximum prompt/completion lengths, gradient accumulation, KL coefficient, logging/checkpointing and accelerator precision settings. Generation-related parameters have a direct multiplicative effect on cost.

GRPOTrainer

The trainer handles generation, reward evaluation, relative-advantage computation and policy optimization. Underneath, it still needs tokenized prompts, model log probabilities and gradients through the policy for sampled completions.

Completion length

Reasoning models can learn to use more tokens when longer deliberation correlates with reward. Monitor average completion length alongside correctness. Runaway verbosity can waste compute and may be a reward artifact rather than better reasoning.

Reward mean

A rising average reward suggests the policy is finding higher-scoring behavior, but inspect whether the reward is trustworthy. If the reward itself is exploitable, improving reward can coincide with worse human-perceived output.

Reward standard deviation

Within-group spread determines the strength of relative comparison. Near-zero variance provides weak advantages. A healthy training log often needs enough diversity that some sampled responses are distinguishably better than others.

KL divergence

Increasing KL indicates the policy is moving away from the reference. Some movement is necessary to improve; sudden large divergence can signal an overly aggressive learning rate, reward pressure or insufficient KL regularization.

Sample generations

Read completions regularly. Metrics can reveal trends, but samples expose reward hacking, malformed reasoning, repeated phrases and answer-format shortcuts immediately.

Practical Exercise to Fine-tune a model with GRPO

A deliberately simple reward, such as a length-oriented signal, makes the mechanics visible. The point is not that response length is a good final objective. It lets you confirm that higher-reward behavior becomes more probable and that training metrics move in the expected direction.

Once the pipeline works, replace toy rewards with task-grounded verification. Always inspect samples before and after training; a model can optimize a numeric reward in an obviously undesirable way.

Why use LoRA with GRPO

Start with a toy reward

Use optimized loading/training plus structured rewards for a more resource-efficient reasoning experiment.

Unsloth integrates optimized model loading, quantization, LoRA, and fast generation with TRL workflows. This is useful because GRPO spends substantial time generating several completions per prompt; faster generation can materially change experiment feasibility.

The exercise uses a structured reasoning/answer format and several reward functions. One reward checks correctness, another can enforce answer type, while format rewards encourage the model to place reasoning and final answers in the desired structure. This demonstrates multi-objective reward design.

Reward weights implicitly define priorities. If a formatting reward is much easier or larger than correctness reward, the model may learn immaculate tags around wrong answers. Inspect each reward component separately and test adversarial outputs that satisfy formatting without solving the task.

Quantization and LoRA reduce memory, but they do not remove the need to monitor numerical stability, sequence lengths, generation count, and reward quality.

Why Unsloth appears

GRPO repeatedly generates several responses, so inference speed and memory dominate practical experimentation. Unsloth provides optimized model loading, quantization, LoRA integration and generation paths that can reduce the resources required for this workflow.

Load a quantized base

Keeping a large frozen base in a low-bit format reduces weight memory, leaving room for longer sequences, more generations or adapter training. The exact supported quantization and hardware path depends on the current Unsloth/Transformers stack.

Attach LoRA

Trainable LoRA modules provide the policy's adaptable parameters. Choose rank and target projections, then verify the number of trainable parameters rather than assuming the adapter was inserted correctly.

Reasoning output format

The exercise uses a structured format that separates reasoning and final answer. A predictable structure makes reward parsing easier because the verifier can locate the final answer without trying to infer it from arbitrary prose.

Correctness reward

Compare the parsed final answer with the known solution using the most robust equivalence check available. For numerical/math tasks, normalize formatting or use symbolic comparison where necessary so cosmetically different correct answers are not punished.

Answer-type reward

A secondary reward can encourage the final response to have the expected type or parseability. This is useful when correctness checking requires an integer, expression or another structured object.

Strict format reward

A strict reward can require exact reasoning/final-answer tags or delimiters. This teaches output structure but is easy to game: a response can have perfect tags and a wrong answer.

Soft format reward

A softer reward gives partial credit when the intended markers/order appear without requiring an exact string. Soft rewards can provide a gradient of learning early in training before the model consistently follows the full format.

Balance reward components

Log correctness and format rewards separately. If format climbs rapidly while correctness stays flat, reduce its relative influence or strengthen the correctness signal. The model will optimize whatever is easiest under the numerical reward.

Fast generation

Optimized generation is particularly valuable because each prompt produces a group of completions. Saving 30% on generation time can matter more than micro-optimizing the gradient step.

Export the adapter/model

After training, save the LoRA adapter with its base-model reference and tokenizer/chat-format requirements. For deployment, decide whether to keep the adapter separate or merge/export to a serving-compatible artifact.
